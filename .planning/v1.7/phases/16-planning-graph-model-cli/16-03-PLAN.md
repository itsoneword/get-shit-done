<objective>
Fix the confirmed root cause of Phase 16's one verification gap: `get-shit-done/bin/lib/frontmatter.cjs`'s `extractFrontmatter` selects the LAST `---...---` pair found ANYWHERE in a document (via `content.matchAll` with no start anchor), instead of the frontmatter block anchored at the file's start. Because `matchAll` scans the whole document, any file whose body also contains an even number of `---` divider lines (this repo's own SUMMARY.md template: a Deviations-section divider + a closing footer divider) makes the "last match" a garbage slice from deep in the body, so the parser silently returns `{}` and the file loses 100% of its frontmatter fields — not just `requires`/`affects`. 16 of 64 real SUMMARY.md files in this repo hit this, including `16-02-SUMMARY.md` itself, which is why `plan:16-01 --provides--> plan:16-02` never appears in the live graph and Phase 16's success criterion 3 ("all edge types present in this repo's own tree") fails on the `provides` type.

Why this is the right fix (not a workaround in `graph.cjs`): the bug is upstream, in a shared parser used by ~15 other call sites (`cmdFrontmatterGet/Set/Merge/Validate`, `graph.cjs`'s own PLAN/todo readers, `roadmap.cjs`, etc.) — patching only `graph.cjs`'s SUMMARY reader would leave every other consumer exposed to the same silent-data-loss failure mode on any file using a body `---` divider (a common markdown convention, not unique to SUMMARY.md).

The original "use the LAST block" logic exists for a real, different reason: CRLF-related double-writes can stack two complete frontmatter blocks back-to-back AT THE START of a file (`---\nold\n---\n---\nnew\n---\nbody`), and picking the most recent (last) stacked block is the correct recovery behavior for THAT scenario. This plan's fix must anchor selection to file-start stacking specifically, preserving that recovery path, while refusing to treat a body `---` divider as part of the stack.


with:

```js
function extractFrontmatter(content) {
  const frontmatter = {};
  // Frontmatter block(s) must be anchored at the START of the file (a real
  // YAML frontmatter block is always first). If multiple blocks are stacked
  // back-to-back at the very start (corruption from a CRLF-related double
  // write producing "---\nold\n---\n---\nnew\n---"), keep unwrapping and
  // use the LAST stacked block, since it represents the most recent state
  // sync. A '---' divider appearing later in the document BODY (e.g. a
  // SUMMARY.md "Deviations" section divider or a footer line) is never part
  // of this stacking and must never be mistaken for a frontmatter block —
  // this anchoring is the Phase 16 gap-closure fix (16-VERIFICATION.md).
  let rest = content;
  let match = null;
  for (;;) {
    const m = rest.match(/^\s*---\r?\n([\s\S]*?)\r?\n---/);
    if (!m) break;
    match = m;
    rest = rest.slice(m.index + m[0].length);
    if (!/^\s*---\r?\n/.test(rest)) break;
  }
  if (!match) return frontmatter;
```

Nothing below the `if (!match) return frontmatter;` line changes — `match[1]` is still the captured YAML body, consumed identically by the existing line-parsing loop.

**Why this works:** each loop iteration matches `^\s*---\r?\n(...)\r?\n---` ONLY against `rest`, which starts at the file's beginning (or, on subsequent iterations, immediately after the previous matched block) — never against the whole remaining document body. After matching a block, the loop peeks at what immediately follows (allowing only whitespace) to decide whether another block is stacked right there; if not, it stops. A body divider that has non-whitespace prose before it (any real Markdown body) can never satisfy `^\s*---` at that position, so it's structurally impossible for it to be picked up as a second stacked block. This has been hand-verified against: the real 16-02-SUMMARY.md (previously returned `{}`, now returns the full frontmatter object), a stacked-corruption fixture (`---\nold: 1\n---\n---\nnew: 2\n---\nBody.` → resolves to `{new: '2'}`, matching the original intent), the CRLF variant of the same, and every existing test in `tests/frontmatter.test.cjs` (empty-frontmatter, no-frontmatter, frontmatter-only-no-body cases all still behave identically).
