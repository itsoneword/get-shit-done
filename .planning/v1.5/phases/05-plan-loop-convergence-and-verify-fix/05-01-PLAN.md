<objective>
Fix `parseMustHavesBlock` (`get-shit-done/bin/lib/frontmatter.cjs`) so `gsd-tools verify artifacts` and `gsd-tools verify key-links` work on real plans. Today the parser hardcodes the block header at 4-space indent, list items at 6, continuation keys at 8+, nested arrays at 10+. Real plans (and every plan this project ships) use HALF that — `must_haves:` at column 0, child keys at 2-space, items at 4-space, continuation keys at 6-space, nested arrays at 8-space — so every current plan returns `[]` ("No must_haves.artifacts found") for both subcommands. This is a v1.4 carry-over blocker logged in STATE.md.

The fix is to **generalize to N-space**: detect the `must_haves:` child indent dynamically and parse the block **relative** to it. This works for the real 2-space plans AND the existing 4-space test fixtures, and is immune to future template reflow. It does NOT touch `parseVerifyCommands` (a separate, already-correct 2-space-aware parser Phase 4 wrote) and does NOT change `verify.cjs` callers (the fix is internal to the parser).

**Critical correctness trap (must not regress):** in real plans the token `artifacts:` appears at TWO indent levels — once nested at 6-space under `truths[0]` (a per-truth artifact list) and once at the top-level 2-space block that `verify artifacts` actually wants. A naive "find `blockName:` at any indent, first match wins" grabs the nested one. Both happen to start with `path: .../init.cjs`, so a "non-empty / contains init.cjs" assertion passes on the WRONG parse (false green). The parser MUST anchor the block header at exactly the `must_haves:` child indent, and the tests MUST assert exact counts (top-level artifacts = 5, key_links = 4) so the nested mis-parse (which yields 1) is caught.
</objective>

Keep the signature, the `[]` fallbacks, the object-item key contract, and the number-coercion (`/^\d+$/` → parseInt) exactly. Concrete algorithm:

1. Extract frontmatter YAML as today: `content.match(/^---\r?\n([\s\S]+?)\r?\n---/)`; return `[]` if no match.
2. **Find the `must_haves:` line** and compute its indent: regex `/^(\s*)must_haves:\s*$/m`. If absent, return `[]`. Let `mhIndent` = length of the captured leading whitespace (normally 0).
3. **Determine the child indent** = the indent of the first non-blank line AFTER `must_haves:` that has indent > `mhIndent`. Call it `childIndent` (2 for real plans, 4 for the existing tests). This is the level at which `truths:`/`artifacts:`/`key_links:` live and is the dynamic replacement for the hardcoded `4`.
4. **Find the block header at EXACTLY `childIndent`:** scan the YAML lines for the first line matching `^\s{${childIndent}}${blockName}:\s*$` where the leading-space count is EXACTLY `childIndent` (not `>=`). This is the anti-collision anchor: it skips the nested `artifacts:` that sits at `childIndent + (itemIndent step)` under a truth. Do NOT use `yaml.search` with a `\s{N}` lower-bound that could match deeper indents. If no header found, return `[]`.
5. **Walk the block body** (lines after the header). Define relative levels off `childIndent`:
   - `itemIndent = childIndent + 2` → list-item dash lines (`- ...`).
   - `keyIndent = childIndent + 4` (and deeper) → continuation `key: value` lines under the current item.
   - `nestedArrIndent = childIndent + 6` (and deeper) → array items under a continuation key.
   - **Termination:** stop when a non-blank line's indent is `<= childIndent` (back to the block-sibling level or shallower — e.g. the next sibling block `key_links:`, or end of must_haves). Blank lines are SKIPPED, not terminators.
6. **Item parsing (mirror current semantics, just at relative indents):**
   - A line matching `^\s{${itemIndent}}-\s+` starts a new item. Push the previous `current` if set.
     - Simple string item (dash value with no `:`): `^\s{${itemIndent}}-\s+"?([^"]+)"?\s*$` and `!line.includes(':')` → `current = thatString`.
     - Else key:value on the dash: `^\s{${itemIndent}}-\s+(\w+):\s*"?([^"]*)"?\s*$` → `current = { [key]: value }`.
   - When `current` is an object, a line matching `^\s{${keyIndent},}(\w+):\s*"?([^"]*)"?\s*$` is a continuation key (use `keyIndent` as a LOWER bound here, matching the current `8,` behavior, because nested `verify:`/`exports:` sub-keys are deeper). Coerce `/^\d+$/` → parseInt.
   - A line matching `^\s{${nestedArrIndent},}-\s+"?([^"]+)"?\s*$` is an array item under the last-added key: convert that key's value to an array and push (mirror current lines 212-221).
   - Push the trailing `current` after the loop.
7. Return `items`.
