Create `get-shit-done/references/receiving-code-review.md`. Faithful port from the superpowers source skill (content extracted in RESEARCH.md Gap 2). The reference MUST contain these sections:

1. **Response Pattern (6 steps), in order:**
   READ → UNDERSTAND (restate the feedback in your own words, or ask) → VERIFY (check the claim against codebase reality) → EVALUATE (is it technically sound for THIS codebase?) → RESPOND (technical acknowledgment or reasoned push-back) → IMPLEMENT (one item at a time, test each).

2. **Forbidden responses** (a "never say these" list):
   - "You're absolutely right!"
   - "Great point!" / "Excellent feedback!" (performative praise)
   - "Let me implement that now" (said *before* verification)

3. **Unclear items rule:** If ANY item is unclear, STOP — do not implement anything yet. "Items may be related. Partial understanding = wrong implementation." Clarify ALL unclear items before implementing ANY.

4. **External-reviewer 5-check** before accepting a suggestion: (1) technically correct for THIS codebase? (2) breaks existing functionality? (3) is there a reason for the current implementation? (4) works on all platforms/versions? (5) does the reviewer understand the full context?

5. **YAGNI check:** grep the codebase for actual usage; if unused, push back: "This endpoint isn't called. Remove it (YAGNI)?" Rule: "You and the reviewer both report to me. If we don't need this feature, don't add it."

6. **Push-back conditions** (push back, with technical reasoning, when): breaks existing functionality; reviewer lacks full context; violates YAGNI; technically incorrect for this stack; legacy/compatibility reasons; conflicts with an architectural decision.

7. **Acknowledge correctly** (no gratitude): "Fixed. [what changed]" | "Good catch — [specific issue]. Fixed in [location]." Delete "Thanks" and state the fix instead.

8. **Gracefully correcting your own push-back:** "You were right — I checked [X] and it does [Y]. Implementing now." State the correction factually, move on.

9. **GitHub thread etiquette:** reply in the comment thread, not as a top-level PR comment.

The reference's own opening line should state WHEN to load it (e.g. "Load this when consuming code-review feedback — from gsd2:review output, a ship-time review, or external PR comments — before implementing any suggestion."), per the artifact-authoring CSO rule.
