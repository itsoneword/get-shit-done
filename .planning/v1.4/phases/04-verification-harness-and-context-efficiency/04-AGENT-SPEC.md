## Agent Roster

| Agent Name | Role | Model Profile | Tools Allowed |
|------------|------|---------------|---------------|
| loop-orchestrator | Drives the verify→investigate→fix loop; counts iterations; fires ceiling-reached handoff; spawns all three workers in fresh contexts | N/A (workflow logic inside execute-phase.md, not a standalone LLM agent) | Task (subagent spawning), Read (plan metadata) |
| loop-verifier | Runs `verify:` commands from PLAN.md `must_haves:`; produces structured pass/fail report in `gaps:` YAML; adapted from gsd-verifier | balanced | Read, Bash (verify commands only), Glob |
| loop-investigator | Reads verifier failure report only (fresh context, no executor history); produces a falsifiable hypothesis with issue classification; never modifies files; adapted from gsd-debugger | balanced | Read, Grep, Glob |
| loop-fixer | Reads investigator hypothesis + plan slice + diff; applies minimal targeted fix; commits via gsd-tools.cjs; adapted from gsd-fixer | balanced | Read, Write, Edit, Bash (gsd-tools.cjs commit only), Grep, Glob |

### Rationale

Four agents, not three: the orchestrator must be named because it owns iteration counting, ceiling-reached handoff, and the fresh-context spawning invariant. Without an explicit orchestrator in the roster, no agent owns those responsibilities and the planner has nowhere to assign them.

Three workers, not one: merging verifier+investigator defeats the primary design constraint documented in CONTEXT.md -- the executor that wrote the code is biased toward its own implementation. The verifier reading only the contract is a structurally different cognitive role. Similarly, the investigator's job is diagnosis (no writes, no fixes); the fixer's job is mutation. Bundling diagnosis and fixing in one agent produces sloppy fixes because the same agent can rationalize a weak hypothesis into a convenient change without being challenged.

Reuse, not new agents: gsd-verifier, gsd-debugger, and gsd-fixer are adapted in loop-invocation mode. Existing standalone usage (``/gsd2:verify-work``, ``/gsd2:debug``, ``/gsd2:fix``) is preserved. The loop adds a tighter input/output contract on top of the existing agents -- it does not replace their interfaces.

## Orchestration Pattern

| Field | Value |
|-------|-------|
| Selected pattern | evaluator-optimizer |
| Reference | `/Users/itsoneword/Downloads/devProjects/GSD/get-shit-done/.claude/get-shit-done/references/AGENTIC-PATTERNS.md` |
| Sub-patterns used | Chain inside the optimizer step (investigator → fixer is a 2-step chain before control returns to the evaluator) |

**Why this pattern fits:** The verifier is the evaluator -- it scores the executor's output against defined criteria (`verify:` commands). The investigator+fixer together are the optimizer -- they improve the output in response to a failing score. The loop continues until the evaluator approves or the iteration ceiling (3) is hit. This maps directly to the Evaluator-Optimizer pattern from AGENTIC-PATTERNS.md: "A generator agent produces output, an evaluator agent scores it against defined criteria, and the loop continues until the evaluator approves or an iteration limit is hit."

One architectural clarification: the executor (generator) sits *outside* the loop -- it ran before the verifier was invoked. The fixer (in-loop optimizer) applies targeted patches to the executor's output rather than regenerating from scratch. This is still Evaluator-Optimizer; the regeneration step is replaced by targeted mutation. The loop is over already-generated code.

**What would break if a simpler pattern were used:** A Chain (no retry) cannot handle the case where the executor's output fails verification -- the loop is the entire point. A bare Orchestrator-Workers pattern has no quality criteria and no iteration ceiling, so it cannot define when "done" is satisfied. Routing does not apply because there is a single input class (failed verification report).

### Rationale

Autonomous/Graph was considered and rejected: the loop has a fixed structure (verifier → investigator → fixer → verifier) and a hard iteration ceiling. Graph adds state machine complexity, cycle detection overhead, and observability cost that buys nothing here. The pattern selection checklist in AGENTIC-PATTERNS.md stops at Evaluator-Optimizer for "iterative refinement against measurable criteria" -- that is exactly this system.

## Communication Contracts

### Contract: loop-orchestrator → loop-verifier

**Sender:** loop-orchestrator
**Receiver:** loop-verifier

**Message shape:**

```json
{
  "plan_path": "string",
  "task_id": "string",
  "verify_commands": [
    {
      "cmd": "string",
      "expect": "string",
      "type": "unit | integration | e2e"
    }
  ],
  "must_haves_slice": [
    {
      "truth": "string",
      "artifacts": ["string"],
      "verify": [
        { "cmd": "string", "expect": "string", "type": "string" }
      ]
    }
  ],
  "iteration": "number",
  "trace_id": "string",
  "debug_file_path": "string | null"
}
```

**Malformed message handling:** loop-verifier rejects invocation with structured error if `verify_commands` is empty or missing. Error written to loop debug file at `debug_file_path` (if present) and surfaced to orchestrator as a non-recoverable ceiling-reach -- the plan has no commands to run. Orchestrator surfaces this to the user immediately without consuming iterations.

### Contract: loop-verifier → loop-orchestrator

**Sender:** loop-verifier
**Receiver:** loop-orchestrator

**Message shape:**

```json
{
  "status": "pass | fail",
  "iteration": "number",
  "trace_id": "string",
  "score": "number",
  "total": "number",
  "gaps": [
    {
      "truth": "string",
      "status": "failed",
      "reason": "string",
      "cmd": "string",
      "actual_output": "string",
      "expected": "string"
    }
  ]
}
```

**Malformed message handling:** If verifier returns output that cannot be parsed into this shape (missing `status`, `trace_id`, or `gaps`), orchestrator treats it as a verification failure with `reason: "verifier output malformed"`, logs the raw output to the loop debug file, and increments the iteration counter. Does not silently continue.

### Contract: loop-orchestrator → loop-investigator

**Sender:** loop-orchestrator
**Receiver:** loop-investigator

**Message shape:**

```json
{
  "failure_report": {
    "gaps": [
      {
        "truth": "string",
        "reason": "string",
        "cmd": "string",
        "actual_output": "string",
        "expected": "string"
      }
    ],
    "score": "number",
    "total": "number"
  },
  "plan_path": "string",
  "task_id": "string",
  "iteration": "number",
  "trace_id": "string",
  "debug_file_path": "string",
  "prior_fix_attempts": [
    {
      "iteration": "number",
      "hypothesis": "string",
      "commit_hash": "string | null",
      "result": "string"
    }
  ]
}
```

**Critical constraint:** `failure_report` must contain only verifier output -- no executor history, no code context beyond what the verifier observed. This enforces the fresh-context bias-elimination property. Orchestrator must not pass executor work logs or task implementation notes to this agent.

**Malformed message handling:** loop-investigator returns `INVESTIGATION INCONCLUSIVE` with `classification: malformed_input` if `failure_report.gaps` is empty or missing. Orchestrator treats this as non-recoverable and fires ceiling-reached handoff immediately.

### Contract: loop-investigator → loop-orchestrator

**Sender:** loop-investigator
**Receiver:** loop-orchestrator

**Message shape:**

```json
{
  "hypothesis": "string",
  "classification": "current-phase | regression | not-yet-built | unrelated",
  "files_implicated": ["string"],
  "confidence": "high | medium | low",
  "suggested_fix_direction": "string",
  "iteration": "number",
  "trace_id": "string",
  "debug_file_path": "string"
}
```

**Non-recoverable classification:** If `classification` is `not-yet-built` or `unrelated`, orchestrator fires ceiling-reached handoff immediately regardless of iteration count. These classifications mean the loop cannot fix the problem -- surfacing the issue to the user is the only correct response.

**Malformed message handling:** If investigator output lacks `hypothesis` or `classification`, orchestrator logs raw output to debug file and fires ceiling-reached handoff without attempting a fix.

### Contract: loop-orchestrator → loop-fixer

**Sender:** loop-orchestrator
**Receiver:** loop-fixer

**Message shape:**

```json
{
  "hypothesis": "string",
  "classification": "current-phase | regression",
  "files_implicated": ["string"],
  "suggested_fix_direction": "string",
  "plan_path": "string",
  "task_id": "string",
  "plan_slice": {
    "truth": "string",
    "artifacts": ["string"]
  },
  "recent_diff": "string",
  "iteration": "number",
  "trace_id": "string",
  "debug_file_path": "string"
}
```

**Malformed message handling:** loop-fixer returns `FIXES PARTIAL` with `reason: "missing hypothesis or plan_slice"` if required fields are absent. Orchestrator fires ceiling-reached handoff. Fixer must never proceed with an empty hypothesis.

### Contract: loop-fixer → loop-orchestrator

**Sender:** loop-fixer
**Receiver:** loop-orchestrator

**Message shape:**

```json
{
  "status": "fixed | partial | skipped",
  "commit_hash": "string | null",
  "files_changed": ["string"],
  "fix_summary": "string",
  "iteration": "number",
  "trace_id": "string"
}
```

**Malformed message handling:** If fixer output cannot be parsed or `status` is absent, orchestrator logs to debug file and fires ceiling-reached handoff -- no blind retry of an unknown fixer state.

### Contract: loop-orchestrator → user (ceiling-reached)

**Sender:** loop-orchestrator
**Receiver:** human (via execute-phase.md CHECKPOINT REACHED block)

**Message shape:**

```json
{
  "type": "ceiling-reached",
  "task_id": "string",
  "plan_path": "string",
  "iterations_attempted": "number",
  "debug_file_path": "string",
  "chronological_narrative": [
    {
      "iteration": "number",
      "verifier_result": "string",
      "investigator_hypothesis": "string",
      "fixer_commit": "string | null",
      "re_verify_result": "string"
    }
  ],
  "final_gaps": [
    {
      "truth": "string",
      "reason": "string"
    }
  ]
}
```

This handoff renders as a ``## CHECKPOINT REACHED`` block with `type: ceiling-reached`. The executor pauses indefinitely until the user responds. Default behavior: block (never default-approve or default-deny -- the failure is genuinely ambiguous).

### Rationale

Structured JSON contracts between agents serve two purposes: they are the parsing contract the planner will code against, and they are the observability artifact that makes failures diagnosable. Every field in the contracts above is present because either (a) the receiver needs it to do its job, or (b) the debug file needs it to reconstruct what happened during a failed run.

The `trace_id` field threads through every message. Without it, iteration 2's failure cannot be correlated with iteration 1's output in the debug file. The `iteration` counter in every message prevents the orchestrator from confusing out-of-order completions if subagent timing varies.

The `prior_fix_attempts` field in the orchestrator→investigator contract is how the investigator avoids re-hypothesizing what was already tried. Without this, iteration 2 investigator produces the same hypothesis as iteration 1, leading to the same fix and the same failure in a tight loop.

## Human-in-the-Loop Boundaries

| Decision Point | Gate Type | Trigger Condition | Timeout Behavior |
|----------------|-----------|-------------------|------------------|
| Ceiling reached | escalation | `iteration_count == 3 AND last verify failed` | Block indefinitely -- executor pauses, no default-approve. The failure requires human judgment. |
| Non-recoverable classification | escalation | Investigator returns `classification: not-yet-built` or `unrelated` | Block immediately -- loop cannot resolve these. Present narrative of single attempt. |
| Verifier malformed input | escalation | `verify_commands` is empty or missing in PLAN.md | Block immediately -- plan is incomplete. User must add `verify:` block before loop can run. |

### Rationale

Exactly one HITL gate type (escalation) rather than approval or notification: the loop is designed to be silent when it succeeds -- the value is removing the human from the happy path. When the loop escalates, it is because the loop genuinely cannot resolve the situation, and the user needs to either take over manually, redesign the approach, or override and continue. An approval gate would add unnecessary latency on every successful iteration. A notification-only gate would leave the executor in an undefined state (is it safe to continue?). Block-on-escalation is the only behavior that gives the user clear ownership of the decision.

Ceiling = 3 is a hard constant, not configurable per-plan. Configurability would create plans that silently raise the ceiling without visibility. User confirmed this choice in CONTEXT.md.

## Memory Strategy

| Memory Type | Scope | Storage Mechanism | Eviction Policy |
|-------------|-------|-------------------|-----------------|
| short-term | per-agent | In-context window only | Destroyed at end of agent turn (by design -- fresh context invariant) |
| persistent cross-iteration | shared (orchestrator owns write, others read) | `.planning/debug/{plan-slug}-verify-loop.md` -- reuses gsd-debugger's debug file pattern | Created at loop start, archived after loop closes (pass or ceiling-reached) |
| iteration counter | orchestrator state | In-memory within orchestrator workflow turn | Not persisted -- orchestrator workflow does not exit between iterations |

### Rationale

The fresh-context invariant means each agent's in-context short-term memory is deliberately discarded between turns. This is the core bias-elimination mechanism, not a limitation. The consequence is that cross-iteration evidence (what was hypothesized, what was fixed, what failed) must be written to a persistent file before each agent turn ends -- otherwise iteration N cannot learn from iteration N-1.

The `.planning/debug/{plan-slug}-verify-loop.md` file is the single source of truth for the loop's history. It is structured identically to gsd-debugger's debug file (known pattern, no new tooling required) with additional fields for loop-specific data: `iteration_count`, `attempts[]` (each containing verifier result, investigator hypothesis, fixer commit, re-verify result).

The orchestrator does not persist its iteration counter to disk because the orchestrator workflow turn spans all iterations -- it does not exit and re-enter between them. If the orchestrator crashes mid-loop (context reset), the debug file provides enough information to reconstruct what happened; the user would restart from a CHECKPOINT REACHED state.

## Observability & Evaluation

### Tracing

GSD has no existing distributed tracing stack (no OpenTelemetry, no Langfuse, no LangSmith). The established pattern in the codebase is structured file-based artifacts (VERIFICATION.md, SUMMARY.md, debug files). The loop uses the same convention: **structured tagged log lines written to the loop debug file** at `.planning/debug/{plan-slug}-verify-loop.md`.

Each significant event is logged as a structured line with fields: `ts` (ISO timestamp), `trace_id`, `iter` (iteration number), `agent` (which agent), `event` (boundary|tool|output|error), `payload_summary` (non-sensitive summary of what passed). Full payloads are not logged inline -- the `gaps` array returned inline in the verifier message is sufficient for the investigator; the debug file records the summary so a developer can trace what each iteration found without bloating the loop file.

Spans captured:
- `loop.start`: orchestrator fires, plan_path and task_id logged
- `agent.spawn`: which agent, which iteration, which files_to_read passed
- `agent.return`: which agent, status, summary of output
- `boundary.validate`: whether message shape parsed correctly
- `loop.end`: final status (pass | ceiling-reached | non-recoverable), total iterations

### Boundary Logging

| Boundary | What gets logged | State tracked | Format |
|----------|------------------|----------------|--------|
| orchestrator → loop-verifier | `verify_commands` count, `iteration`, `trace_id` | Iteration counter, files_to_read list | Structured line in loop debug file |
| loop-verifier → orchestrator | `status`, `score`, `gaps` count, `iteration`, `trace_id` | Verification report path | Structured line + report path reference |
| orchestrator → loop-investigator | `gaps` count, `prior_fix_attempts` count, `iteration`, `trace_id` | No executor context passed (logged as absent -- auditable) | Structured line in loop debug file |
| loop-investigator → orchestrator | `classification`, `confidence`, `files_implicated` count, `iteration`, `trace_id` | Classification value (non-recoverable triggers early exit) | Structured line in loop debug file |
| orchestrator → loop-fixer | `hypothesis` first 100 chars (truncated for log), `files_implicated`, `iteration`, `trace_id` | Plan slice summary | Structured line in loop debug file |
| loop-fixer → orchestrator | `status`, `commit_hash`, `files_changed` count, `iteration`, `trace_id` | Commit hash (auditable in git log) | Structured line in loop debug file |
| orchestrator → user (ceiling-reached) | Full `chronological_narrative`, `final_gaps`, `debug_file_path` | All iterations complete | CHECKPOINT REACHED markdown block |

### Failure Diagnosis

| Agent | Failure detection signal | Where to look | Common root causes |
|-------|--------------------------|---------------|--------------------|
| loop-orchestrator | Iteration counter exceeds 3 without status=pass; non-recoverable classification received; message parse error from any agent | `.planning/debug/{plan-slug}-verify-loop.md` -- `boundary.validate` lines | Empty verify_commands in PLAN.md; investigator returning non-recoverable classification; fixer commit failing |
| loop-verifier | `status: fail` in output; missing `gaps` field; Bash command returning non-zero with no output | Loop debug file `agent.return` line for agent=verifier; `gaps` array in returned message | Verify command references service not running; shell env missing; verify schema missing from PLAN.md |
| loop-investigator | Missing `hypothesis` or `classification`; `INVESTIGATION INCONCLUSIVE` in output | Loop debug file `agent.return` line for agent=investigator; `debug_file_path` in investigator context | Failure report was empty (malformed verifier output propagated); files_implicated outside current plan scope |
| loop-fixer | `status: skipped` or missing `commit_hash`; TypeScript type errors after edit; gsd-tools.cjs commit returns non-zero | Loop debug file `agent.return` line for agent=fixer; `git log --oneline -5` in plan working dir | Hypothesis required editing a shared interface with many consumers (blast radius too wide); file path in hypothesis not found |

### Rationale

The loop debug file is the diagnostic artifact that enables a developer to reproduce a failed run from disk alone: it contains every agent's input summary, output summary, classification decisions, and commit hashes. Without this file, a three-iteration ceiling-reached failure produces only the final markdown report -- the developer cannot see what iteration 1 tried, why iteration 2 took a different hypothesis, or whether the fixer actually committed.

"Standard logging" was explicitly rejected in the AGENT-SPEC checker criteria. The structured tagged lines at each boundary give the checker something concrete to validate: if the boundary log line for `orchestrator → loop-investigator` contains an `executor_context` field, the fresh-context invariant was violated, and that is now detectable from the log.

## Reflection & Self-Correction

| Field | Value |
|-------|-------|
| What triggers reflection | loop-verifier returns `status: fail` (automated), or loop-investigator returns non-recoverable classification (orchestrator decision, not agent reflection) |
| Metrics checked | Verifier score (verified/total), classification value from investigator, commit presence from fixer |
| What happens on failure | Orchestrator feeds failure report to loop-investigator; loop-investigator feeds hypothesis to loop-fixer; loop-fixer patches and commits; orchestrator re-invokes loop-verifier in fresh context |
| Iteration limit | 3 -- hard ceiling, not configurable per-plan |
| Tied to evaluation criteria | Test Contracts: TC-LOOP-PASS, TC-LOOP-RECOVER, TC-LOOP-CEILING |

### Rationale

The loop *is* the self-correction mechanism -- it is not a layer on top of it. Each agent in the loop does not self-reflect; the orchestrator's outer loop is what produces reflection behavior at the system level. Individual agents are designed to be stateless and unbiased precisely because they do not carry prior iteration context.

The iteration ceiling prevents the infinite loop failure mode described in AGENTIC-PATTERNS.md Evaluator-Optimizer: "Evaluator never approves -- loops to iteration limit and returns last attempt with low confidence." Ceiling = 3 was chosen to give the loop one genuine retry (iteration 1: baseline, iteration 2: first fix, iteration 3: second fix if first was wrong) without burning unbounded tokens.

## Security & Permission Boundaries

| Agent | Allowed Tools | Denied Tools | Scope Constraints |
|-------|---------------|--------------|-------------------|
| loop-orchestrator | Task (subagent spawn), Read (plan metadata only) | Write, Edit, Bash (direct execution), all destructive tools | Reads only PLAN.md and loop debug file; all other reads delegated to spawned agents |
| loop-verifier | Read, Bash (only commands present in `verify_commands` from PLAN.md), Glob | Write, Edit, Git | Bash scope: commands parsed from `verify:` block only -- no arbitrary shell; output captured and returned, not executed further |
| loop-investigator | Read, Grep, Glob | Bash, Write, Edit, Git, WebSearch | File reads scoped to `files_implicated` list from failure report + PLAN.md; must not read executor work logs or SUMMARY.md from current phase |
| loop-fixer | Read, Write, Edit, Bash (gsd-tools.cjs commit subcommand only), Grep, Glob | Git (direct), WebSearch | Write/Edit scope: only files in `files_implicated` from investigator output + their direct dependencies found by grep; gsd-tools.cjs commit is the only Bash path allowed |

**Prompt injection defense approach:** The highest-risk untrusted input surface is `verify_commands[*].cmd` -- these commands come from PLAN.md (authored by the planner, not user runtime input) and their output is returned to the orchestrator. The verifier must execute these commands but must NOT pass raw command output directly into the investigator prompt. The orchestrator sanitizes: it extracts `actual_output` up to a fixed character limit (1024 chars), wraps it in a delimiter block (`` ```actual_output ... ``` ``), and includes it in the `failure_report` JSON field. This prevents shell command output from escaping the structured field and injecting instructions into the investigator's prompt.

**Input validation strategy:** Validation occurs at the orchestrator (message shape before spawning each agent) and at each agent boundary (each agent checks required fields before proceeding). `verify_commands[*].type` is validated against the enum `unit | integration | e2e` -- unrecognized types are rejected before execution. Shell commands in `verify_commands[*].cmd` are not sanitized (they are planner-authored, not user-provided runtime input) but are executed in a non-interactive subshell with no additional environment injection.

### Rationale

The verifier's Bash permission is the sharpest security decision in this system. Without it, the verifier cannot run integration or e2e commands. With unrestricted Bash, a malicious or malformed verify command (even planner-authored) could execute arbitrary shell. The mitigation is that verify commands are authored at plan time (trusted planner, not runtime user input), but the orchestrator still validates the command list before passing it to the verifier. The output sanitization step (delimiter wrapping, character limit) prevents the most obvious prompt injection path: a server returning a crafted response that includes text resembling LLM instructions.

The investigator is DENIED Bash explicitly because diagnosis must not produce side effects. An investigator that can execute commands can accidentally trigger state changes that corrupt iteration 2's baseline. Read-only tools only.

## Error Handling & Failure Modes

| Failure Scenario | Affected Agent(s) | Detection Method | Recovery Strategy | Fallback Behavior |
|------------------|--------------------|------------------|-------------------|-------------------|
| `verify_commands` empty or missing in PLAN.md | loop-orchestrator, loop-verifier | Orchestrator validates schema before spawning verifier; verifier rejects invocation | Orchestrator surfaces immediate CHECKPOINT REACHED with `type: ceiling-reached` and reason `no_verify_commands` | Block -- executor must not continue; user must add `verify:` block to plan |
| Verifier Bash command exits non-zero with no output | loop-verifier | Command exit code + empty stdout | Verifier records gap with `reason: "verify command failed: [exit code]"`, proceeds to output structured gaps | Loop continues -- fixer may be able to address the underlying cause |
| Verifier output malformed (missing `status` or `gaps`) | loop-orchestrator | Orchestrator message shape validation | Log raw output to debug file; treat as `status: fail` with single synthetic gap `reason: "verifier output malformed"` | Increment iteration; feed synthetic gap to investigator |
| Investigator returns non-recoverable classification | loop-orchestrator | Classification value in investigator output | Orchestrator fires ceiling-reached handoff immediately without consuming remaining iterations | Block with narrative showing classification reason and files implicated |
| Fixer commit fails (gsd-tools.cjs returns non-zero) | loop-fixer | Non-zero exit from commit subcommand | Fixer returns `status: partial, commit_hash: null` with reason | Orchestrator increments iteration; next verifier run will find the same failure; ceiling reached sooner |
| Loop debug file write fails | loop-orchestrator | File write error | Orchestrator logs warning to stdout (only location available), continues loop -- observability degraded but loop is functional | Continue -- loop degraded but not broken; ceiling-reached handoff still fires |
| Model context window approaching limit mid-loop | loop-investigator (most token-intensive) | Context size metric from runtime | Not auto-detected -- investigator should be spawned with `files_to_read` scoped to `files_implicated` only, not full codebase | Loop pauses and surfaces ceiling-reached with note on context size; user must intervene |

### Rationale

Every row in this table represents a failure that *will* happen in practice, not theoretical edge cases. The verifier command failing with no output is the most common -- integration tests fail because a local service is not running. The fixer commit failing is the second-most common -- the fixer edits a file that was concurrently modified by the executor, producing a merge conflict. Both are handled: loop continues in the first case (fixer can address the root cause), loop degrades and reaches ceiling faster in the second (user gets control).

The context window row is the only unmitigated failure mode. It is documented here rather than silently ignored. The mitigation (tight `files_to_read` scoping) is a constraint on the orchestrator's message construction, not an agent-level fix. If this becomes a problem in practice, the investigator should be split into a separate shallow pass (file list) + deep pass (analysis), but that is out of scope for v1.

## Reasoning & Planning Approach

- **Orchestrator:** hardcoded sequence per iteration (verify → investigate → fix → verify). Iteration count drives the only branching decision. No dynamic decomposition -- the orchestrator always dispatches the same three workers in the same order.
- **loop-verifier:** pre-planned chain -- reads `verify_commands`, executes each as a Bash command, compares output against `expect`, aggregates pass/fail. No LLM reasoning on individual commands; LLM synthesizes the structured gaps output.
- **loop-investigator:** ReAct-style reasoning over the failure report and implicated files -- forms hypothesis, reasons about evidence, produces a structured conclusion. Explicitly DOES NOT take actions; reasoning only.
- **loop-fixer:** plan-then-act -- reads hypothesis, plans the minimal change, executes edit+commit. No iteration within the fixer's own turn.
- **Sequencing:** all sequencing decisions belong to the orchestrator. Agents do not decide what runs next.
- **Intermediate plans:** the loop debug file exposes the investigator's hypothesis and the fixer's fix summary before the next verification runs. A developer can inspect the file mid-loop to understand what is happening. The file is also the mechanism for the ceiling-reached narrative.
- **Fresh context as a prompting technique:** each agent's `<files_to_read>` block is constructed by the orchestrator to include exactly what that agent needs -- no more. The orchestrator must NOT pass executor prompts, SUMMARY.md, or implementation context to the verifier or investigator. This is an explicit constraint on prompt construction, not a convention.
- **Planner note:** the `verify_after: true` task attribute and the `verify:` block in `must_haves:` are the plan-time contracts that drive this system. The planner must document how authors add these to PLAN.md and what happens if neither is present on a given task.

## Test Contracts

### Contract: loop-verifier -- pass on all verify commands

| Field | Value |
|-------|-------|
| Agent | loop-verifier |
| Input | Orchestrator message with `verify_commands` containing one command that will exit 0 with output matching `expect` |
| Preconditions | PLAN.md has valid `verify:` block; verify command is runnable in current environment |
