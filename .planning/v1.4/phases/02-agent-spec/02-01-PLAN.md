Create `get-shit-done/references/AGENTIC-PATTERNS.md` with this structure:

TITLE: `# Agentic System Topology Patterns`

DESCRIPTION: Reference catalog for the gsd-agent-researcher. When a user describes an agentic system, map it to the simplest pattern that works. Challenge upgrades to more complex patterns unless the user can justify the added complexity.

SOURCES LINE: Anthropic "Building Effective Agents" (5 workflow patterns + augmented LLM), Andrew Ng's 4 Agentic Design Patterns (Reflection, Tool Use, Planning, Multi-Agent Collaboration).

SUMMARY TABLE (all 6 patterns in one table):

| Pattern | Complexity | When to Use | When NOT to Use |
|---------|-----------|-------------|-----------------|
| Chain (Augmented LLM) | Low | Linear transformations, extraction, summarization | Needs retry, branching, or parallel work |
| Routing | Low-Medium | Diverse input types needing different handling | Single input type, or when misclassification is catastrophic |
| Parallel | Medium | Independent subtasks, results merged | Tasks depend on each other's output |
| Orchestrator-Workers | Medium-High | Complex tasks needing dynamic decomposition | Simple fixed pipelines, or when orchestrator becomes bottleneck |
| Evaluator-Optimizer | Medium-High | Quality-sensitive outputs with definable criteria | Criteria are subjective or undefined, risk of infinite loops |
| Autonomous / Graph | High | Long-horizon tasks, uncertain environments, conditional branching | Anything simpler works, team lacks observability tooling |

ONE DETAILED SECTION PER PATTERN (`## Pattern Name`), ordered simplest to most complex. Each section contains:

1. **Description** -- 2-3 sentences explaining the pattern
2. **Architecture diagram** -- ASCII text showing agent flow (not Mermaid, keep it simple and portable)
3. **Real-world example** -- one concrete example (use GSD's own workflows where possible, e.g. "GSD's discuss-phase -> plan-phase -> execute-phase is a Chain pattern")
4. **Tradeoffs table** with Advantage | Disadvantage columns
5. **Failure modes** -- bulleted list of what goes wrong and how to detect it
6. **Observability requirements** -- what MUST be logged/traced for this pattern to be debuggable, specific to the topology
7. **Upgrade signal** -- when to consider moving to a more complex pattern
8. **Downgrade signal** -- when this pattern is overkill (omit for Chain since it's the simplest)

The 6 patterns in order:
1. Chain (Augmented LLM) -- linear sequence, each step builds on previous
2. Routing -- classifier routes input to specialized subagents
3. Parallel -- independent subagents run simultaneously, results merged
4. Orchestrator-Workers -- central orchestrator assigns subtasks to specialized workers
5. Evaluator-Optimizer -- agent generates, evaluator scores, loop continues
6. Autonomous / Graph -- full state machine with conditional branching

CLOSING SECTIONS:

`## Combining Patterns` -- Most real systems combine patterns. Example: "Orchestrator-Workers where one worker uses Evaluator-Optimizer internally." The AGENT-SPEC should name the primary pattern and note any sub-patterns used within it.

`## Pattern Selection Checklist` -- 6 questions the researcher should ask:
1. Can the task be done in a single pass with no branching? -> Chain
2. Do different inputs need different handling? -> Routing
3. Are there independent subtasks? -> Parallel
4. Does the task need dynamic decomposition? -> Orchestrator-Workers
5. Does output quality need iterative refinement? -> Evaluator-Optimizer
6. Is the environment uncertain with conditional paths? -> Autonomous/Graph
