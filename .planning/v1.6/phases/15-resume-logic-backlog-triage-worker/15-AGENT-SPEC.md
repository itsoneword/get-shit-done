# Phase 15 -- Agent System Design Contract

> Architecture contract for agentic system phases. Generated by gsd-agent-researcher, verified by gsd-agent-checker. Each section captures WHAT was decided and WHY -- so failures trace back to design intent.

---

## Agent Roster

| Agent Name | Role | Model Profile | Tools Allowed |
|------------|------|---------------|---------------|
| resume-gate | Orchestrator-level workflow step in autonomous.md: detects a parked-and-answered phase, reads the snapshot, runs the staleness gate, and either re-parks (drift) or hands off to resume-replay | quality (inherits from the running orchestrator session) | Read (STATE.md, ROADMAP.md, cross-phase-notes.md), Bash (gsd-tools park staleness --raw, gsd-tools mailbox list --raw), Write (phase CONTEXT.md decisions block) |
| resume-replay | Orchestrator-level workflow step in autonomous.md: receives the staleness-clean handoff, writes the superseding ledger record, re-enters the blocked workflow step with the answer injected as a locked decision | quality (inherits from the running orchestrator session) | Read (phase CONTEXT.md, parked snapshot), Bash (gsd-tools ledger append --data, gsd-tools park staleness --raw), Write (phase CONTEXT.md decisions block) |
| triage-worker | Workflow step in overnight.md (and standalone /gsd2:triage command): reads pending todos + ROADMAP backlog items, analyzes each against the codebase and roadmap, assigns one six-verdict with evidence, appends one proposal per item to MAILBOX.jsonl | quality (inherits from the running orchestrator session) | Read (todos/pending/ dir, ROADMAP.md, relevant codebase files), Bash (gsd-tools list-todos --raw, gsd-tools mailbox append --data), WebSearch (evidence gathering, optional) |
| inbox-triage-presenter | Orchestrator-level step within the existing /gsd2:inbox skill: presents triage-type mailbox entries as proposals (distinct from parked-phase questions), accepts human accept/defer, records the verdict, prints the routing command | quality (inherits from the running orchestrator session) | Read (MAILBOX.jsonl via gsd-tools mailbox list --raw), Bash (gsd-tools mailbox answer --id --answer) |

### Rationale

These are not spawned subagents -- the fundamental constraint (locked Phase 10/CLAUDE.md) is that GSD subagents lack Skill/Agent tool grants; supervision logic runs at orchestrator level only, in workflow prose executed by the top-level session or headless `claude -p` run. "Agent" here means a named workflow step or branch inside an existing workflow file, with defined I/O contracts, not a Task() spawn.

The four-step decomposition is forced by two independent data flows and a hard inbox constraint:

**Why not collapse resume-gate and resume-replay into one step?** Because they have different abort conditions and different write targets. resume-gate reads the staleness diff and makes the proceed-or-re-park decision. If it decides to re-park (drift), no ledger write should happen and the workflow emits `PHASE RESULT: parked phase=N q=q-NEW` and stops. resume-replay owns the ledger superseding record write, which must happen exactly once when the branch proceeds. Merging them means either the ledger write happens before the drift decision (wrong -- it's premature) or the diff check is entangled with the ledger write (wrong -- the pure-function staleness check becomes coupled to I/O). The split preserves the Phase 12 invariant: the ledger gets its superseding record when the branch ACTS on the answer.

**Why not collapse triage-worker and inbox-triage-presenter?** Triage writes proposals; the inbox presents them. These run at different times (triage runs during the overnight phase loop; the inbox runs the next morning). Merging them would require the overnight run to block waiting for human input, which destroys the overnight-then-morning design. The thin-inbox lock (Phase 12) is also structural: the inbox never plans, executes, or mutates planning files. The inbox step is an extension of the already-existing inbox skill, not a new agent.

**Why not spawn a separate codebase-analysis subagent for triage?** Triage reads maybe 10-20 todo items against a codebase it has in context from the overnight run. The evidence gathering is grep-depth (list-todos, grep key terms), not multi-turn exploration. A spawned subagent would add coordination overhead, require Task() grants the system lacks, and produce no quality benefit over the orchestrator session doing it inline. Chain-level inline tool calls are sufficient.

## Orchestration Pattern

| Field | Value |
|-------|-------|
| Selected pattern | routing |
| Reference | `/home/cleversol/gsd2/mine/.claude/get-shit-done/references/AGENTIC-PATTERNS.md` |
| Sub-patterns used | Chain within each route (resume-gate -> resume-replay is a two-step chain; triage-worker is a chain of per-item verdict assignments) |

**Why this pattern fits:** Two different input types (a parked-and-answered phase, vs. a pending todo/backlog item) need different handling, and the routes are known up front. The autonomous.md `execute_phase` step already acts as a router -- it inspects phase state and branches: new phase goes to discuss/plan/execute; parked-and-answered phase goes to the resume route. The overnight.md finish step already provides a natural insertion point for the triage route after the phase loop. Routing is exactly the AGENTIC-PATTERNS.md description: "Do different inputs need different handling, with the routes known up front?" Yes on both counts.

**What would break if a simpler pattern were used:** A pure Chain would require the same linear path for every phase execution, which cannot accommodate the parked-phase case without adding a conditional branch -- which is exactly what Routing adds. Without the routing branch, autonomous.md would either re-run a parked phase from scratch (discarding the park apparatus's entire purpose) or silently skip it (losing forward progress). Neither is acceptable. Chain is insufficient because the branching is structural, not incidental.

### Rationale

The initial temptation is to call this Orchestrator-Workers because it orchestrates several named "workers." That framing is rejected because: (1) the orchestrator does not dynamically decompose tasks -- routes are fixed and predetermined; (2) there is no feedback loop from workers back to the orchestrator influencing next dispatch; (3) the four steps run in two entirely separate workflow files at separate times, not in a single coordinated dispatch session. Routing + Chain inside each route is the honest description.

Autonomous/Graph was considered because autonomous.md already IS a state machine with cycles (the iterate step). The resume splice does not add new states to that machine -- it adds a conditional branch inside the existing `execute_phase` step. Adding a branch inside an existing step is Routing, not a new graph node. The Autonomous pattern would be an overclaim that implies the phase loop's topology is being redesigned; it is not.

## Communication Contracts

All workflow-prose "agents" in this phase communicate via filesystem artifacts (JSONL files, JSON snapshot files, markdown) and gsd-tools CLI calls. The contracts below define the exact CLI input/output shapes at each boundary, because these are the actual message channels between steps.

### Contract: mailbox-answer -> resume-gate

**Sender:** The human via `gsd-tools mailbox answer` (or `/gsd2:inbox` calling it)
**Receiver:** resume-gate (the branch-detection logic inside autonomous.md `execute_phase`)
**Trigger:** A subsequent overnight run (or manual `--phase N` re-run) after a question has been answered

**Message shape -- mailbox record (what resume-gate reads via `gsd-tools mailbox list --raw`):**

```json
{
  "id": "q-NNN",
  "run_id": "overnight-YYYYMMDD-HHMMSS",
  "phase": 15,
  "question": "string — the parked question text",
  "context": "string — criterion + condition that fired",
  "options": ["option A", "option B"],
  "evidence": "string",
  "status": "answered",
  "answer": "string — the human's settled answer",
  "answered_ts": "2026-06-17T10:00:00.000Z",
  "ts": "2026-06-16T23:05:00.000Z",
  "decision_id": "string or null"
}
```

**Trigger condition for resume route (read by resume-gate from snapshot + mailbox):**
- Snapshot file exists at `.planning/run/{run-id}/parked/phase-{N}.json`
- The mailbox record whose `id` matches `snapshot.question_id` has `status === "answered"`

**Malformed message handling:** If the mailbox record for `snapshot.question_id` is absent or its `status` is not `"answered"`, resume-gate does NOT enter the resume route. It treats the phase as still-parked and emits `PHASE RESULT: parked phase=N q=<question_id>` (the existing parked-phase outcome). This is fail-safe: a phase wrongly treated as still-parked is reviewable; a phase wrongly replayed against an unanswered question could poison downstream work.

### Rationale

The snapshot's `question_id` is the join key between the park artifact and the mailbox record. This join is intentional -- it was established in Phase 12. A missing join (snapshot references a q-id that does not exist in the mailbox) means the snapshot was written but the mailbox append failed -- a Phase 12 invariant violation. resume-gate treats it as still-parked because the question is genuinely unanswered from the system's perspective.

### Contract: resume-gate -> resume-replay (park staleness output)

**Sender:** resume-gate (calls `park staleness --raw` and evaluates the result)
**Receiver:** resume-replay (proceeds if `changed` is empty; re-parks otherwise)

**Message shape -- `park staleness <run-id> --phase N --raw` JSON output:**

```json
{
  "phase": 15,
  "question_id": "q-NNN",
  "resume_instruction": "re-enter question_triage with the answer to q-NNN applied as the decision for '<topic>'",
  "changed": ["ROADMAP.md"],
  "unchanged": ["STATE.md", "cross-phase-notes.md", "CONTEXT.md"],
  "missing": [],
  "git_range": "abc1234..HEAD"
}
```

**Proceed condition (resume-gate evaluates):**
- `changed` is empty AND `missing` is empty: proceed to resume-replay
- `changed` is non-empty OR `missing` is non-empty (headless): re-park with a "state moved since park" note

**Re-park message appended to mailbox on drift:**

```json
{
  "question": "Phase N parked branch cannot resume: planning state moved since park. Re-answer with current context.",
  "phase": "N",
  "context": "Staleness check at resume: changed=ROADMAP.md git_range=abc1234..HEAD. Original question was: <question text>. Original answer was: <answer text>.",
  "status": "pending"
}
```

**Malformed message handling:** If `park staleness --raw` exits non-zero or its stdout is not parseable JSON, treat the diff as if `changed` were non-empty (fail-safe: assume drift, re-park). Log the parse failure in run.log as `PHASE_FAILURE phase=N reason=staleness-parse-error` using the existing `PHASE_FAILURE` TYPE token.

### Rationale

The split between interactive and headless drift handling is established in 15-CONTEXT.md decisions: interactive path shows the diff and continues (the human just answered and is watching); headless path re-parks because replaying against moved state blind is a trust violation. The contract above encodes only the headless path because this phase is wired into autonomous.md's harness mode. The interactive path (no GSD_RUN_ID) falls through to the human seeing the staleness output from inbox and deciding, which happens before autonomous.md is ever invoked for resume.

### Contract: resume-gate -> resume-replay (handoff: proceed signal)

**Sender:** resume-gate (after confirming no drift)
**Receiver:** resume-replay

**Handoff (implicit in-context state, since both are steps in the same workflow session):**

```
{
  snapshot fields in context: phase, blocked_at, question_id, resume_instruction,
                               phase_dir, context_path,
  answer: "<the settled answer text from the mailbox record>",
  staleness_result: { changed: [], unchanged: [...], missing: [], git_range: "..." }
}
```

**resume-replay actions, in order:**
1. Write the answer as a locked decision into the phase CONTEXT.md `<decisions>` block (the answer must not be re-asked during replay)
2. Call `gsd-tools ledger append --data <superseding-record>` (the superseding record references the original question's decision_id)
3. Re-enter the workflow step named in `resume_instruction` (e.g. `question_triage`) with the answer applied

**Superseding ledger record shape (written by resume-replay):**

```json
{
  "decision": "<the topic/question resolved by the answer>",
  "alternatives": ["<original options from the mailbox record, if present>"],
  "evidence": "Resumed after human answered q-NNN: <answer text>",
  "confidence": "HIGH",
  "escalated": null,
  "supersedes": "<original decision_id or q-NNN>",
  "phase": "N"
}
```

**Malformed message handling:** If the CONTEXT.md write fails (file not writable), abort resume and emit `PHASE RESULT: failed phase=N reason=context-write-error`. If `ledger append` fails, abort resume and emit `PHASE RESULT: failed phase=N reason=ledger-write-error`. Never replay the blocked step without the superseding record and the locked answer being written first -- these are the audit trail.

### Rationale

Writing the answer to CONTEXT.md before replaying is the mechanism that prevents re-asking. The replayed discuss/plan step reads CONTEXT.md decisions to know what is already settled; if the answer is absent from CONTEXT.md, the step will treat the question as open and ask again -- defeating the entire purpose. The ledger superseding record is a Phase 10/12 invariant: the ledger gets its record when the branch acts on the answer. Writing it after the replay step would mean a crashed replay leaves no audit trace of the decision.

### Contract: triage-worker -> MAILBOX.jsonl

**Sender:** triage-worker (appends one proposal per todo/backlog item)
**Receiver:** inbox-triage-presenter (reads MAILBOX.jsonl via `gsd-tools mailbox list --raw` during the morning inbox session)

**Triage proposal mailbox record shape (appended via `gsd-tools mailbox append --data`):**

```json
{
  "question": "Triage proposal: <todo title or backlog item B-label>",
  "phase": null,
  "context": "triage-verdict: <already-done|obsolete|fold-into-phase|new-phase|needs-input|defer>",
  "options": ["accept", "defer"],
  "evidence": "<one-paragraph rationale: why this verdict, citing code location or roadmap reference>",
  "status": "pending",
  "decision_id": null
}
```

**Distinguishing field:** The `context` field MUST begin with the prefix `triage-verdict:` so inbox-triage-presenter can distinguish triage proposals from parked-phase questions (which have a `context` referencing the escalation criterion that fired). The prefix is the type discriminator; no new schema field is added (the inbox is already built to handle non-decision-type entries).

**Verdict values (exactly six, verbatim from TRIAGE-01):**
- `already-done` — evidence points to existing code or completed phase
- `obsolete` — the need no longer exists per roadmap or codebase evidence
- `fold-into-phase` — the work belongs in an existing active or upcoming phase (name the phase)
- `new-phase` — the work is real but large enough to warrant a new roadmap phase
- `needs-input` — cannot assign a verdict without human clarification
- `defer` — valid work but not a priority for the current milestone

**Per-item write call:**

```bash
node "$HOME/.claude/get-shit-done/bin/gsd-tools.cjs" mailbox append --data \
  '{"question":"Triage proposal: <title>","context":"triage-verdict: <verdict> target=<phase or reason>","options":["accept","defer"],"evidence":"<rationale>","status":"pending"}'
```

**Batch-atomicity:** `appendFileSync` is POSIX-atomic under 4096 bytes per line. One `mailbox append` call per item. No batch transaction is needed -- each line is independently atomic. A partial triage run (e.g. crash after item 3 of 10) leaves items 1-3 in the mailbox and items 4-10 absent; the inbox session will see the partial set. This is acceptable because triage is idempotent at re-run (a second `/gsd2:triage` run will propose the missing items again, producing duplicate proposals for items 1-3 that the human will see as already-accepted or already-deferred). The planner may add a deduplication guard (check if a proposal for the same title already exists and is pending) but this is Claude's discretion.

**Malformed message handling:** If `mailbox append` exits non-zero for an item, log the failure in run.log as `PHASE_FAILURE phase=triage reason=mailbox-append-failed item=<title>` and continue to the next item (do not abort the entire triage run for one failed item). If the run completes with N failed appends, include the count in the finish log.

### Rationale

Using the `context` field prefix as the type discriminator avoids schema migration. The inbox already reads all pending entries regardless of type (Phase 12 locked: "do not hardcode decision-type-only assumptions"). A separate `entry_type` field would be cleaner but requires updating `cmdMailboxAppend` validation -- schema stability was locked in Phase 10. A prefix on an existing string field achieves the same discrimination without touching the schema.

### Contract: inbox-triage-presenter -> human (accept/defer routing)

**Sender:** inbox-triage-presenter (the step inside /gsd2:inbox that handles triage-prefix entries)
**Receiver:** human, then records the verdict via `gsd-tools mailbox answer`

**What inbox-triage-presenter shows for each triage proposal:**

```
---
Triage Proposal {q-NNN}
Verdict: <verdict>  Target: <phase or reason>

Item: <todo title or backlog item>
Evidence: <rationale text>

Options:
  A. accept — print routing command and mark answered
  B. defer — leave for a future triage session (mark answered with "deferred")
```

**On accept -- `gsd-tools mailbox answer <run-id> --id q-NNN --answer "accepted: <verdict>"`:**

The inbox prints the routing command for the accepted verdict:

| Verdict | Routing command printed |
|---------|-------------------------|
| `already-done` | `gsd-tools todo mark-done <todo-id>` (or manual: mark todo file status done) |
| `obsolete` | `gsd-tools todo remove <todo-id>` (or manual: delete from todos/pending/) |
| `fold-into-phase` | `gsd-tools todo move-to-phase <todo-id> <target-phase>` (or manual: move to phase backlog) |
| `new-phase` | `gsd-tools roadmap add-phase "<title>" "<goal>"` (or manual: add to ROADMAP.md backlog) |
| `needs-input` | `# No command — provide input and re-run /gsd2:triage` |
| `defer` | `# No command — item remains in pending` |

**Key constraint:** The inbox prints the command; it does NOT execute it. The human runs it as a separate explicit step. This is the propose-never-dispose invariant -- a REQUIREMENTS.md Out-of-Scope constraint locked before this phase.

**Malformed message handling:** If a mailbox entry has `context` starting with `triage-verdict:` but the verdict token is not one of the six, inbox-triage-presenter shows it as `needs-input` with a warning: "(unknown verdict token in triage entry -- treating as needs-input)". This prevents a corrupt entry from blocking the inbox session.

### Rationale

The routing-command-printed-not-executed shape is the only design that satisfies both the thin-inbox lock and the propose-never-dispose constraint. One-click accept-and-execute was explicitly evaluated and rejected during the discuss phase (15-CONTEXT.md deferred ideas: "rejected for v1 (breaks the thin-inbox lock + propose-never-dispose)"). The two-step shape (accept records + prints command; human runs command) is symmetric with resume being a separate step from inbox, which the user confirmed is the right posture.

## Human-in-the-Loop Boundaries

| Decision Point | Gate Type | Trigger Condition | Timeout Behavior |
|----------------|-----------|-------------------|------------------|
| Morning answer to parked-phase question | approval | A mailbox question with `status: "pending"` is presented in /gsd2:inbox | No timeout in interactive inbox session; question remains pending until explicitly answered or deferred |
| Staleness diff shown before replay | notification | resume-gate runs staleness check; changed or missing files are surfaced before resume-replay fires | Interactive path: human is present and decides inline. Headless path: no human present; re-park instead of proceeding (this is the timeout behavior -- default-deny for headless drift) |
| Triage proposal accept/defer | approval | A triage-verdict mailbox entry is shown in the inbox | No timeout; entry remains pending until explicitly accepted or deferred in the inbox |
| Routing command execution after accept | explicit human step | Human accepted a triage verdict; inbox printed the command | No timeout; the command is printed and waits for human to run it manually |

### Rationale

Human gates are required at the answer and accept steps because these are the HITL moments the entire harness was designed for. The staleness diff boundary is a notification (not a blocking approval) in the interactive path -- the human is already present and the diff is informational context for the answer they're about to give. In headless mode, re-parking is the timeout behavior: the system defaults to denying forward motion rather than replaying against unknown drift. The routing-command step has no timeout because it is fully deferrable -- the human can run it later. Adding an in-session timeout would require a persistent daemon or polling loop, both of which are out of scope (REQUIREMENTS.md: no persistent daemon).

## Memory Strategy

| Memory Type | Scope | Storage Mechanism | Eviction Policy |
|-------------|-------|-------------------|-----------------|
| short-term | per-orchestrator-session | In-context window of the running autonomous.md or overnight.md session | Session ends; no persistence |
| persistent (park snapshot) | per-run, per-phase | `.planning/run/{run-id}/parked/phase-{N}.json` | Never evicted automatically; cleaned up when the phase is complete (planner may add a cleanup step, Claude's discretion) |
| persistent (mailbox) | per-run | `.planning/run/{run-id}/MAILBOX.jsonl` | Append-only; no eviction. Records accumulate for the lifetime of the run |
| persistent (ledger) | per-run | `.planning/run/{run-id}/DECISIONS.jsonl` | Append-only; write-once; no eviction |
| persistent (run-meta) | per-run | `.planning/run/{run-id}/RUN-META.json` | Rewritten at phase boundaries (not evicted); used for stuck detection |
| retrieval (codebase context for triage) | per triage-worker invocation | Read-on-demand via Bash (grep, Read tool) during the triage step | Not persisted; re-read on each triage run |

### Rationale

All persistent state lives in `.planning/run/{run-id}/` -- this is the Phase 10 layout locked before any other v1.6 phase. Phase 15 adds no new storage locations and no new file formats. The park snapshot, mailbox, and ledger are already implemented primitives (Phases 12, 10 respectively). The memory strategy here is: don't add memory; wire the existing memory artifacts. The codebase context for triage is read-on-demand because a triage run executes at most once per overnight run, involves at most a few dozen items, and the codebase state must reflect the current tree (not a stale snapshot). Caching it would be premature optimization with no measurable benefit.

## Observability & Evaluation

### Tracing

This system uses three existing observability channels, all locked in prior phases. No new channel is introduced.

1. **run.log** -- the 16-token TYPE vocabulary (locked Phase 13). Every significant transition in the overnight run is a typed run.log line. Resume and triage events are logged using existing tokens only (no new tokens may be invented per the locked vocabulary). Diagnostic grep: `grep 'TYPE_TOKEN' .planning/run/{run-id}/run.log`.

2. **DECISIONS.jsonl** -- append-only per-run ledger (locked Phase 10). Every decision the harness makes autonomously is appended here. The resume superseding record is the decision event for the resumed branch. Diagnostic: `gsd-tools ledger list <run-id>`.

3. **MAILBOX.jsonl** -- append-only per-run mailbox (locked Phase 10/12). All parked questions and triage proposals are entries here. Diagnostic: `gsd-tools mailbox list <run-id> --raw`.

The three channels together constitute the full observability surface. A failed run can be diagnosed entirely from these three files without replaying any transcript -- this is the "auditable from the ledger alone" guarantee from STATE.md key decisions.

### Boundary Logging

| Boundary | What gets logged | What state is tracked | Format |
|----------|------------------|------------------------|--------|
| resume-gate detects answered snapshot | run.log `PHASE_START phase=N` (existing token, already written by overnight.md before invoking autonomous --phase N) | snapshot existence, mailbox answer status | `<ISO8601-UTC> PHASE_START phase=N worktree=...` |
| resume-gate: drift detected, re-parking | run.log `PHASE_PARKED phase=N q=q-NEW` after new mailbox append | staleness `changed` list embedded in the new mailbox entry's `context` field | `<ISO8601-UTC> PHASE_PARKED phase=N q=q-NEW` |
| resume-gate: staleness-parse-error | run.log `PHASE_FAILURE phase=N reason=staleness-parse-error` | raw stdout of failed park staleness call | `<ISO8601-UTC> PHASE_FAILURE phase=N reason=staleness-parse-error` |
| resume-replay: CONTEXT.md write failed | run.log `PHASE_FAILURE phase=N reason=context-write-error` | none (write failed before ledger) | `<ISO8601-UTC> PHASE_FAILURE phase=N reason=context-write-error` |
| resume-replay: ledger write failed | run.log `PHASE_FAILURE phase=N reason=ledger-write-error` | none | `<ISO8601-UTC> PHASE_FAILURE phase=N reason=ledger-write-error` |
| resume-replay: replay complete | run.log `PHASE_COMPLETE phase=N` (if the replayed step reaches a passed verification) | superseding ledger record in DECISIONS.jsonl | `<ISO8601-UTC> PHASE_COMPLETE phase=N` |
| triage-worker: item appended | MAILBOX.jsonl entry with `context: "triage-verdict: <verdict>"` | evidence string in mailbox entry | one JSONL line appended |
| triage-worker: mailbox append failed | run.log `PHASE_FAILURE phase=triage reason=mailbox-append-failed item=<title>` | item title preserved in reason | `<ISO8601-UTC> PHASE_FAILURE phase=triage reason=mailbox-append-failed item=<title>` |
| inbox-triage-presenter: accept recorded | MAILBOX.jsonl record updated via `mailbox answer` (status: answered, answer: "accepted: <verdict>") | verdict and routing command preserved in answer field | one JSONL full-file rewrite (Phase 12 pattern) |

### Failure Diagnosis

| Agent/Step | Failure detection signal | Where to look | Common root causes |
|------------|--------------------------|---------------|-------------------|
| resume-gate | Phase still shows as parked after a supposed answer | `gsd-tools mailbox list <run-id> --raw` — check status field for the question_id in the snapshot; check that `parked/phase-N.json` exists | mailbox answer not recorded (inbox session was interrupted), snapshot file missing (park.cjs write failed during the parking event), run-id mismatch between the snapshot and the mailbox query |
| resume-gate | `PHASE_FAILURE reason=staleness-parse-error` in run.log | run.log, then stdout of `gsd-tools park staleness <run-id> --phase N` | park.cjs non-zero exit (snapshot file malformed or missing after overnight file modifications), JSON parse error from malformed snapshot |
| resume-replay | `PHASE_FAILURE reason=context-write-error` in run.log | CONTEXT.md file permissions, disk space | worktree not writable (sandbox restriction), context_path in snapshot points to non-existent directory, disk full |
| resume-replay | `PHASE_FAILURE reason=ledger-write-error` in run.log | `gsd-tools ledger append` stderr, DECISIONS.jsonl permissions | GSD_RUN_ID not set at replay time (gate failure upstream), run directory not initialized |
| triage-worker | Fewer mailbox entries than expected items | `gsd-tools mailbox list <run-id> --raw` — count triage-verdict prefixed entries; compare to `gsd-tools list-todos --raw` count + ROADMAP backlog B-item count | partial triage run (crash after N items), mailbox append failures logged as PHASE_FAILURE in run.log |
| inbox-triage-presenter | Triage entries shown as unknown-verdict | `gsd-tools mailbox list <run-id> --raw` — inspect `context` field for malformed verdict tokens | triage-worker wrote an invalid verdict token (not one of the six), context field prefix missing |

### Rationale

All diagnostic paths resolve to two commands (`gsd-tools mailbox list --raw` and `grep TYPE_TOKEN run.log`) plus reading the snapshot file. This was a deliberate constraint from Phase 13: "auditable from the ledger alone without replaying transcripts." If a developer cannot reproduce a failure by reading these three artifacts, either an artifact is missing (the failure is in the write path, not the logic) or the observability is insufficient. The boundary log table above ensures every transition writes to at least one of the three artifacts.

## Reflection & Self-Correction

| Field | Value |
|-------|-------|
| What triggers reflection | re-park (resume-gate detects drift): the system reflects "state moved, this answer may be stale" and routes to a new parked question rather than proceeding |
| Metrics checked | staleness diff output: `changed` and `missing` arrays from `park staleness --raw` |
| What happens on failure | re-park with a "state moved since park" note appended to the mailbox; the run continues to independent phases |
| Iteration limit | One re-park per resume attempt. A re-parked phase is NOT re-entered in the same run. The next overnight run that detects the re-parked question as answered will re-evaluate drift again. This caps at one drift re-park per run, preventing cascading re-parks. |
| Tied to evaluation criteria | TC-3 (headless drift re-park), TC-4 (clean staleness proceeds to replay) |

Triage-worker has no self-correction loop. Each item gets exactly one verdict with evidence in a single pass. If the verdict is wrong, the human corrects it by deferring (leaving it pending) or by the human providing context via the `needs-input` routing command. This is correct for a propose-only worker: the human IS the correction mechanism.

### Rationale

The reflection mechanism for resume is minimal and correct: one drift check, one re-park if dirty, no retry loop. A retry loop would require reading the mailbox again for the same question, which is meaningless -- the human's answer doesn't change between the initial drift check and a retry. Drift is a structural fact about the planning files, not a model output quality issue. This is the "wrong and obvious" failure mode from AGENTIC-PATTERNS.md evaluator-optimizer section: it needs a guardrail (re-park), not reflection.

## Security & Permission Boundaries

| Agent/Step | Allowed Tools | Denied Tools | Scope Constraints |
|------------|---------------|--------------|-------------------|
| resume-gate | Read (CONTEXT.md, STATE.md, ROADMAP.md, cross-phase-notes.md, parked snapshot), Bash (gsd-tools park staleness --raw, gsd-tools mailbox list --raw) | Write (any planning file before drift check passes), Bash (git operations, file deletion), ledger append | May only read from `.planning/` and the phase directory; must not write before staleness check completes |
| resume-replay | Write (phase CONTEXT.md decisions block only), Bash (gsd-tools ledger append, gsd-tools park staleness --raw), Read (phase CONTEXT.md, snapshot) | Write (ROADMAP.md, STATE.md, MAILBOX.jsonl), Bash (any shell exec not listed, git push, file deletion) | May only modify the specific phase's CONTEXT.md; ledger append scoped to `GSD_RUN_ID` run |
| triage-worker | Read (todos/pending/ dir, ROADMAP.md, codebase files for evidence), Bash (gsd-tools list-todos --raw, gsd-tools mailbox append --data), WebSearch (evidence gathering) | Write (todos/pending/ files, ROADMAP.md, any planning artifact), Bash (file deletion, git operations) | Propose-only: may append to MAILBOX.jsonl, may not modify todo files or ROADMAP.md; evidence-read codebase files are read-only |
| inbox-triage-presenter | Read (MAILBOX.jsonl via gsd-tools mailbox list --raw), Bash (gsd-tools mailbox answer --id --answer) | Write (ROADMAP.md, todos/pending/, CONTEXT.md, any file other than MAILBOX.jsonl via the answer CLI), Bash (routing command execution) | mailbox answer scoped to `GSD_RUN_ID` run; inbox prints routing commands, never executes them |

**Prompt injection defense approach:** The primary injection surface is the mailbox `question` and `context` fields, which contain user-provided and harness-generated text that gets rendered in the inbox session. Defense: these fields are presented as data, not as instructions. The inbox workflow reads them via `gsd-tools mailbox list --raw` and displays them verbatim inside a labeled block structure (`---\nQuestion {q-NNN}\n...\n`). The orchestrator session treats the displayed content as text to summarize and discuss, not as commands to execute. This is instruction-hierarchy enforcement: the workflow prompt is the instruction; mailbox content is subordinate data. No additional sanitization layer is implemented because GSD operates in a single-user trusted context (the user's own planning artifacts) -- injection from an external malicious actor would require compromising MAILBOX.jsonl directly, which is a file-system-level attack outside the model's threat model.

For the triage worker's codebase reads: file content read during evidence gathering is similarly treated as data (read to find evidence for a verdict) not as instructions to follow. The triage-worker's verdict-assignment logic is driven by the workflow prompt, not by file content.

**Input validation strategy:** Validated at the tool boundary by the existing gsd-tools primitives:
- `mailbox append --data <JSON>`: validates `question` field present; rejects missing required fields (Phase 10 invariant)
- `park staleness --raw`: validates snapshot file exists and is parseable JSON; exits non-zero on failure (resume-gate catches this as parse-error)
- `ledger append --data`: validates required ledger fields; rejects missing fields (Phase 10 invariant)
- The `triage-verdict:` prefix in `context` is validated at presentation time by inbox-triage-presenter (unknown prefix treated as `needs-input`)

### Rationale

The deny lists above enforce propose-never-dispose structurally: triage-worker and inbox-triage-presenter cannot physically execute disposal operations (they are not granted those tool calls). The architecture makes the invariant explicit, not just aspirational prose. If a model drift or prompt injection caused either step to attempt a write to ROADMAP.md or a todo deletion, the tool call would either not be in the allowed set (and Claude Code would not execute it) or would be a bug in the workflow prose that violates this spec -- either way it is detectable from the tool-call log rather than silent.

## Error Handling & Failure Modes

| Failure Scenario | Affected Agent(s) | Detection Method | Recovery Strategy | Fallback Behavior |
|------------------|--------------------|------------------|-------------------|-------------------|
| Mailbox record for snapshot.question_id absent or not answered | resume-gate | `gsd-tools mailbox list --raw` returns no record with matching id and status=answered | Treat phase as still-parked | `PHASE RESULT: parked phase=N q=<question_id>` -- the overnight runner's skip-to-independent logic treats parked as non-fatal and continues |
| `park staleness --raw` exits non-zero or stdout not valid JSON | resume-gate | Non-zero exit or JSON.parse throws | Treat as drift (fail-safe: assume changed) | Re-park with "staleness check failed" note; log `PHASE_FAILURE reason=staleness-parse-error` |
| Planning files changed since park (headless context) | resume-gate | `changed` or `missing` non-empty in staleness output | Re-park with "state moved since park" note appended to mailbox | New q-NNN created; `PHASE RESULT: parked phase=N q=q-NEW` |
| CONTEXT.md write fails before replay | resume-replay | Node.js fs.writeFileSync throws | Abort replay; do NOT write ledger (no partial audit trail) | `PHASE RESULT: failed phase=N reason=context-write-error`; phase added to BLOCKED in overnight runner |
| Ledger append fails after CONTEXT.md write | resume-replay | gsd-tools ledger append exits non-zero | Abort replay; CONTEXT.md now has the answer but ledger does not | `PHASE RESULT: failed phase=N reason=ledger-write-error`; phase added to BLOCKED. Note: CONTEXT.md has the answer written -- re-running resume will see the decision already in CONTEXT.md and may skip writing it, but ledger will still be missing. Planner should add idempotency check on the ledger write. |
| Replayed step fails (e.g. discuss-phase --auto emits PHASE PARKED again) | resume-replay | `PHASE RESULT: parked phase=N q=q-NEW-NNN` in skill output | The replayed step produced a new park (a new question arose during replay) | New parked question appended to mailbox; `PHASE RESULT: parked phase=N q=q-NEW-NNN`. This is correct behavior: replay may surface new questions. |
| Individual triage mailbox append fails | triage-worker | gsd-tools mailbox append exits non-zero | Log `PHASE_FAILURE reason=mailbox-append-failed item=<title>` and continue to next item | Partial triage proposals in mailbox; re-running triage will re-propose the failed items (idempotent at re-run with possible duplicates) |
| Unknown verdict token in triage entry | inbox-triage-presenter | `context` prefix starts with `triage-verdict:` but token not in six-verdict set | Show entry as `needs-input` with warning | Human sees the proposal with degraded verdict; can defer or accept as needs-input |
| GSD_RUN_ID not set during resume or triage in headless context | resume-gate, triage-worker | gsd-tools commands that require run context exit non-zero with "no run context" error | This should never happen in correctly-wired overnight.md; if it does, treat as `PHASE_FAILURE` | `PHASE RESULT: failed phase=N reason=no-run-context`; developer must check that overnight.md exports GSD_RUN_ID before invoking autonomous --phase N |

### Rationale

The ledger-write-after-CONTEXT-write failure (row 5) is the trickiest: CONTEXT.md now has the answer but the ledger does not. This creates an inconsistency where the file state is ahead of the audit trail. The recovery is to add an idempotency check in resume-replay: before writing CONTEXT.md, check if a superseding ledger record already exists for this question_id. If it does (a previous attempt succeeded on ledger but crashed on some subsequent step), skip the ledger write on re-run. This is planner-level design -- the spec flags it as a gap the planner must address rather than specifying the exact implementation.

The "new park during replay" row is not a failure -- it is correct behavior. Phase 15 does not guarantee that a replayed step will complete without new questions; it guarantees that existing questions are not re-asked and that the answer is applied. A new question from a new branching point is a new park-and-ask cycle, which the existing harness handles correctly.

## Reasoning & Planning Approach

- **resume-gate reasoning:** Pre-planned conditional: read snapshot, query mailbox, evaluate staleness output. No LLM reasoning required for the gate itself -- it's field reads and comparisons. The only LLM judgment call is interpreting `resume_instruction` (a human-readable string like "re-enter question_triage at step 3b with the answer to q-001 applied"). The planner should make the resume_instruction format machine-readable enough that interpretation is unambiguous (e.g., include the step name and the question_id explicitly). This is marked as Claude's discretion in 15-CONTEXT.md.

- **triage-worker reasoning:** ReAct-style inline for each item: read item → read codebase evidence (grep/file reads) → assign verdict → write proposal. The LLM drives the evidence gathering and verdict assignment. The workflow prompt constrains the verdict to the six-token set; the LLM must justify its choice with a concrete evidence string (file path + line, phase reference, or roadmap entry). A verdict without evidence string is a malformed proposal -- the workflow prose should validate this before calling `mailbox append`.

- **Sequencing:** resume-gate runs inside `execute_phase` in autonomous.md (at the top of the step, before 3a smart_discuss, because resume short-circuits the normal discuss/plan/execute path). triage-worker runs in overnight.md finish step, after the phase loop and before/with the morning report. inbox-triage-presenter runs inline in the inbox skill's `present_and_discuss` step, interleaved with parked-phase questions based on mailbox order.

- **Intermediate plans exposed:** The staleness diff is shown inline before replay (SC1 wording), making the gate decision visible. Triage evidence strings are included in the mailbox proposals, making the verdict reasoning inspectable without running the triage worker again.

- **Prompting approach:** No few-shot examples are required for the gate steps (they are deterministic field reads). The triage-worker verdict assignment benefits from in-prompt guidance: a brief table of the six verdicts with one-line criteria (e.g. "already-done: evidence of implementing code or completed phase found in codebase") should be included in the overnight.md triage step prompt to constrain drift across runs.
