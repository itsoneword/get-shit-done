# Phase 13 -- Agent System Design Contract

> Architecture contract for the Overnight Runner (`/gsd2:overnight`). Generated by gsd-agent-researcher, verified by gsd-agent-checker. Each section captures WHAT was decided and WHY -- so failures trace back to design intent. Decisions marked [LOCKED] come from 13-CONTEXT.md and are not relitigable by the planner.

---

## Agent Roster

| Agent Name | Role | Model Profile | Tools Allowed |
|------------|------|---------------|---------------|
| overnight-runner | Top-level harness session executing `workflows/overnight.md`: health check, run init, sequential phase loop, worktree lifecycle, conflict routing, run.log authorship, report trigger | balanced | Bash (sandboxed), Read, Skill(gsd2:autonomous) |
| autonomous-loop | Existing `workflows/autonomous.md` discuss→plan→execute loop, invoked per phase as a sub-skill in the same session; inherits `GSD_RUN_ID`/`GSD_RUN_LOG` from env | per existing workflow (unchanged) | Existing grants (Read, Write, Edit, Bash, Task/Agent for planner+executor subagents) |
| inbox-reviewer | Existing `/gsd2:inbox` morning session, extended with a run-report header (reads same run-id artifacts via `gsd-tools run report`) | balanced | Bash (gsd-tools mailbox/run), Read |

**Not agents (tool boundary, not agent boundary):** `gsd-tools run init/snapshot/report`, `gsd-tools worktree add/merge/remove`, `gsd-tools ledger append/list`, `gsd-tools mailbox append/list/answer`, `gsd-tools park create/staleness`. These are deterministic CLI primitives shipped in Phases 7/10/11/12. `gsd-tools run report` is the one NEW primitive this phase adds (in ledger.cjs).

### Rationale

Could one agent do this? Almost -- and that is the point. The overnight-runner and autonomous-loop run in the **same session** (overnight wraps autonomous via `Skill(skill="gsd2:autonomous")` [LOCKED]); they are listed as separate roster entries because they have different responsibilities, different failure signatures, and a real contract boundary (env vars + skill args in, phase outcome out). Merging them -- rewriting the phase loop inline in overnight.md -- was explicitly rejected in CONTEXT.md ("the autonomous phase loop itself is not rewritten inline") because it duplicates a shipped, tested loop and creates drift between interactive and overnight behavior.

The inbox-reviewer is separate because it runs in a *different session at a different time* (morning, interactive) and must work from persisted artifacts alone -- that constraint (RUN-04: no transcript replay) is the load-bearing reason it cannot share state with the runner except through `.planning/run/{run-id}/` files.

What the roster deliberately excludes: gsd-planner/gsd-executor subagents spawned inside autonomous-loop. They are unchanged by this phase; their contracts live in autonomous.md's existing design. Constraint reminder: GSD subagents lack Skill/Agent tool grants, so the runner MUST execute at orchestrator level (top-level session or headless `claude -p`), never as a spawned subagent [LOCKED, REQUIREMENTS.md Out of Scope].

## Orchestration Pattern

| Field | Value |
|-------|-------|
| Selected pattern | chain |
| Reference | `/home/cleversol/gsd2/mine/.claude/get-shit-done/references/AGENTIC-PATTERNS.md` |
| Sub-patterns used | Routing inside each phase's discuss step (escalation contract three-tier verdict classifier, shipped Phase 11); park-don't-block as the external partial-failure handler |

**Why this pattern fits:** AGENTIC-PATTERNS.md names GSD's discuss→plan→execute as the canonical Chain example. Phase 13 wraps that chain in a *deterministic sequential iterator*: roadmap-ordered phases, one at a time, each in its own worktree [LOCKED: "Phases execute sequentially in v1"]. Control flow is fixed and unidirectional per phase; the iterator order comes from ROADMAP.md `depends_on`, not from runtime LLM decomposition. Per the selection checklist, question 1 ("single pass, no branching?") fails only on predefined failure branches -- and those are handled by the harness primitives, not by topology.

**What would break if a simpler pattern were used:** Nothing -- Chain IS the simplest pattern. The challenge ran the other direction (see Rationale).

### Rationale

**Challenge log -- patterns considered and rejected:**

- **Orchestrator-Workers (rejected).** "Runner" language suggests it, but the runner always dispatches the same worker (autonomous-loop) in the same roadmap order. AGENTIC-PATTERNS.md downgrade signal applies verbatim: "If the orchestrator always dispatches the same workers in the same order, you have a Chain disguised as an orchestrator -- collapse to Chain and remove the indirection." Skip-to-independent is not dynamic decomposition; it is a precomputed dependency-graph walk (`depends_on` parse from ROADMAP.md) with a fixed rule: on park/failure, advance to the next phase not depending on the blocked one [LOCKED].
- **Autonomous/Graph (rejected).** The run is long-horizon, but there are no cycles, no dynamic node selection, and no state-driven re-planning in v1. Concurrent independent phases (which would force Parallel) are explicitly deferred [LOCKED, Deferred Ideas].
- **Chain's documented failure mode -- "mid-chain error halts the entire chain, no fallback" -- is the one real weakness, and it is exactly what Phases 10-12 built compensation for:** park-and-ask routes blockers to MAILBOX.jsonl and the run continues (PARK-01); stuck detection flags non-progress (PARK-04); auth failure is the *deliberate* hard stop (RUN-03). The chain stays simple because recovery lives in the harness, not the topology.

Consequence for debugging: a failed run reads linearly. run.log is a single timeline; `grep PHASE_` shows exactly where the chain stopped and why. An Orchestrator-Workers design would have bought nothing and cost that linear trace.

## Communication Contracts

### Contract: overnight-runner -> autonomous-loop

**Sender:** overnight-runner
**Receiver:** autonomous-loop (same session, sub-skill invocation)
**Message shape:** environment variables + skill arguments (this is the wire format -- there is no JSON payload at this boundary):

```json
{
  "env": {
    "GSD_RUN_ID": "overnight-YYYYMMDD-HHMMSS  (REQUIRED -- the run signal, NOT config; locked Phase 10)",
    "GSD_RUN_LOG": "/abs/path/.planning/run/{run-id}/run.log  (REQUIRED -- absolute, so worktree-CWD phases write to the main tree)"
  },
  "skill_args": {
    "from": "phase number (optional, --from N override)",
    "phase": "single-phase selector for the current iteration"
  }
}
```

**Malformed message handling:** missing `GSD_RUN_ID` is fail-loud by construction -- ledger.cjs and mailbox.cjs run-context gates exit 1 on any append without run context (Phase 10 invariant), so an unwired sub-invocation cannot silently produce an unaudited run. Missing/relative `GSD_RUN_LOG` is the known worktree trap (Open Question 3 in 13-RESEARCH.md): the runner computes it as an absolute path at run init, before any worktree exists, and the health check verifies it is absolute (`case "$GSD_RUN_LOG" in /*) ;; *) HEALTH_FAIL ;; esac`-equivalent).

### Contract: autonomous-loop -> overnight-runner (phase outcome)

**Sender:** autonomous-loop
**Receiver:** overnight-runner (resumes control after the Skill call returns)
**Message shape:** the runner derives a per-phase outcome record and writes it into `RUN-META.json` `phases[]` (the field `cmdRunInit` already creates, ready to populate):

```json
{
  "phase": "13",
  "status": "completed | parked | failed",
  "worktree": "branch-name or \"in-place\" (sandbox fallback)",
  "merge_clean": true,
  "started_ts": "ISO8601 UTC",
  "ended_ts": "ISO8601 UTC"
}
```

Outcome detection inputs, in priority order: (1) `PHASE PARKED` sentinel in the sub-skill's final output (Phase 12 bifurcation contract) -> `parked`; (2) non-zero failure signal / error output -> `failed`; (3) otherwise `completed`. The runner -- not autonomous-loop -- owns writing this record, calling `gsd-tools run snapshot` at every phase boundary, and writing the stuck flag to run.log [LOCKED, Phase 12 boundary decision].

**Malformed message handling:** if the outcome is ambiguous (no sentinel, no clean completion signal), the runner records `status:"failed"` with a `PHASE_FAILURE reason=ambiguous-outcome` run.log line and applies skip-to-independent. Fail-safe direction is "treat as failed", never "assume completed" -- a wrongly-failed phase is reviewable in the morning; a wrongly-completed phase poisons downstream merges.

### Contract: overnight-runner -> MAILBOX.jsonl (conflict + permission routing)

**Sender:** overnight-runner
**Receiver:** inbox-reviewer (asynchronously, next morning), via `gsd-tools mailbox append` (never direct file writes -- q-NNN allocation and run-id enforcement live in mailbox.cjs)
**Message shape** (merge-conflict case, RUN-02):

```json
{
  "question": "Merge conflict in phase {N} ({branch}) — resolve before this branch can land",
  "context": "conflict_files: [list from worktree merge --raw]; run_id: {run-id}; phase: {N}",
  "status": "pending"
}
```

Permission-denial case (probe-confirmed 2026-06-12): two routable signals, both used -- the model writes a mailbox entry mid-session when it sees the denial, AND the runner checks `permission_denials[]` in the `claude -p` result JSON as a backstop, appending an entry per denial (`tool_name`, `tool_input` in context) if the model did not already write one.

**Malformed message handling:** `gsd-tools mailbox append` validates and exits 1 on bad input; the runner treats a failed mailbox append as a `PHASE_FAILURE` (logged, run continues to independent work) -- a conflict that cannot be routed must still never be swallowed, so the run.log `CONFLICT_ROUTED_FAIL` line preserves the evidence even if the mailbox write failed.

### Contract: gsd-tools worktree merge -> overnight-runner (the RUN-02 field read)

**Sender:** `gsd-tools worktree merge {branch} --raw` (tool, but the contract is load-bearing enough to lock here)
**Receiver:** overnight-runner
**Message shape:**

```json
{
  "clean": false,
  "conflict_files": ["path/a", "path/b"]
}
```

**Malformed message handling:** `cmdWorktreeMerge` exits 0 on conflict BY DESIGN (worktree.cjs source comment, line ~16) -- exit-code checking is insufficient and is the canonical swallow bug. The runner MUST parse the JSON and branch on `clean`. If JSON parse fails: treat as conflict (fail-safe), log `MERGE_PARSE_FAIL phase={N}` to run.log, route to mailbox with the raw output in context. Also handled: `cmdWorktreeAdd` returning `{ok:false, fallback:"in-place"}` (sandboxed environments) -> log `WORKTREE_FALLBACK phase={N} mode=in-place` warning, record `worktree:"in-place"` in the phase record, and proceed without isolation.

### Contract: run artifacts -> inbox-reviewer (morning report, RUN-04)

**Sender:** overnight-runner (via persisted artifacts -- no live channel)
**Receiver:** inbox-reviewer / `gsd-tools run report <run-id>`
**Message shape:** the report reads EXACTLY three files and nothing else [LOCKED]:

```json
{
  "RUN-META.json": "started_ts, status, phases[] (per-phase outcome records above)",
  "DECISIONS.jsonl": "per-decision records: decision, alternatives, evidence, confidence, escalated, phase (Phase 10 schema)",
  "MAILBOX.jsonl": "per-question records: id (q-NNN), question, context, status, run_id (Phase 10/12 schema)"
}
```

Report output: plain text, terminal-friendly (exact field layout is Claude's discretion [LOCKED]). `/gsd2:inbox` prints this report as its header then walks the questions -- inbox embeds/reuses `run report`, never duplicates it [LOCKED].

**Malformed message handling:** missing run-id or missing RUN-META.json -> stderr error + exit 1 (matches existing ledger.cjs CLI conventions). A truncated/corrupt JSONL line -> skip the line, count it, print `N unparseable entries skipped` in the report -- the morning report must never crash on one bad line, because it is the only window into the run.

### Rationale

Every boundary uses an artifact that already has an owner and a schema (env vars: Phase 10; mailbox/ledger lines: Phase 10/12; worktree JSON: Phase 7). The one new shape -- the `phases[]` outcome record -- fills a field `cmdRunInit` already reserved, so no schema migration. The recurring design question "what happens when a required field is dropped" has one answer throughout: fail loud and in the failed direction (ambiguous -> failed, unparseable merge -> conflict), because the entire run is unattended and silent optimism is the one unrecoverable error class. Trace key at every boundary is `run_id` (+ `phase`); there is no separate trace_id because run_id already partitions every artifact.

## Human-in-the-Loop Boundaries

| Decision Point | Gate Type | Trigger Condition | Timeout Behavior |
|----------------|-----------|-------------------|------------------|
| ESC-03 calibration gate | approval (pre-run, structural) | Every `/gsd2:overnight` launch: case-SENSITIVE `grep -q "PASS"` on `11-CALIBRATION.md` finds no token | Fail closed -- `HEALTH_FAIL` in run.log, run never starts. No timeout; a human must complete calibration first. |
| Run launch itself | approval (manual-first v1) | User launches `/gsd2:overnight` (interactive or single `claude -p` line); cron line is DOCUMENTED, not installed [LOCKED] | N/A -- nothing runs without the human starting it |
| Park-and-ask verdict / merge conflict / permission denial | escalation (non-blocking) | Escalation contract park verdict; `clean:false` merge; `permission_denials[]` or model-visible denial | Run does NOT block: question parked to MAILBOX.jsonl, branch stops, runner skips to next independent phase; human answers in the morning inbox (resume is Phase 15) |
| Auth failure | notification + hard stop | `authentication_failed` / auth error string / non-zero exit attributable to auth | Run stops immediately, `AUTH_FAILURE` logged loudly, NO silent retry (RUN-03). Human finds it in run.log / morning report. |
| Morning review | notification | Run completes or stops; `/gsd2:inbox` is THE single morning entry point [LOCKED] | Questions wait indefinitely as `pending`; staleness check on resume (Phase 12/15) covers long gaps |

### Rationale

The gates map directly to the trust ladder. ESC-03 is the only *blocking* gate and it earns its latency: it is the structural proof that escalation precision was human-validated before any unattended run -- removing it means the park/proceed classifier runs overnight uncalibrated, and a miscalibrated "proceed" on an irreversible action has no rollback. Every other escalation is deliberately NON-blocking (park-don't-block applied to the run loop [LOCKED]): the cost of blocking overnight is the whole night's throughput; the cost of parking is one morning question. Auth is the asymmetric exception -- retrying auth failures burns the night producing nothing while looking alive, which is worse than stopping (RUN-03's "never silently retrying" is verbatim requirement text). No "just in case" approval gates were added: the workload is research/plan/write in a worktree-isolated local repo; destructive escapes are auto-denied by the sandbox and routed to the mailbox, which IS the approval gate, asynchronously.

## Memory Strategy

| Memory Type | Scope | Storage Mechanism | Eviction Policy |
|-------------|-------|-------------------|-----------------|
| short-term | per-agent (overnight session context; each phase's sub-skill context) | in-context window; fresh per phase iteration | context window; phase boundary resets working context |
| persistent | shared (runner <-> inbox-reviewer, across sessions) | `.planning/run/{run-id}/`: RUN-META.json (runner owns schema), DECISIONS.jsonl + MAILBOX.jsonl (append-only, schemas owned by ledger.cjs/mailbox.cjs since Phase 10), run.log (append-only typed lines, runner owns format), park snapshots (park.cjs owns, Phase 12) | never -- these are the audit artifacts; deleting them breaks "auditable from the ledger alone" |
| persistent | shared (cross-session telemetry) | `.planning/telemetry/agent-trace.jsonl` via `appendFileSync` -- POSIX-atomic under 4096 bytes, so parallel worktree writes need no mutex and no per-run trace files [LOCKED] | existing telemetry policy (manual) |
| retrieval | none | N/A -- planning state (STATE.md, ROADMAP.md, cross-phase-notes.md) is re-read fresh at resume time (Phase 12 staleness contract; resume itself is Phase 15) | N/A |
| isolation | per-phase | git worktree per phase (filesystem-level memory isolation); merged at phase boundary | `worktree remove` after merge |

### Rationale

Schema ownership is already settled by prior phases and this phase must not blur it: ledger.cjs owns DECISIONS.jsonl, mailbox.cjs owns MAILBOX.jsonl, park.cjs never touches MAILBOX.jsonl (Phase 12 boundary), and the runner's only new schema surface is the `phases[]` records inside RUN-META.json plus the run.log line format. If a schema changed mid-run the append-only design saves us: old lines stay valid, readers (report) skip-and-count unparseable lines. The deliberate non-decision: no retrieval/index layer -- the morning report and resume flows read small, bounded files; adding indexing would be infrastructure for a problem that does not exist at this scale (one run-id directory per night).

## Observability & Evaluation

### Tracing

**Tool: typed-line run.log + JSONL ledgers, greppable by design (zero-dependency constraint rules out OTel/Langfuse-class tooling -- and the artifacts ARE the tracing system).** Three layers, all keyed by `run_id`:

1. **`run.log`** (`.planning/run/{run-id}/run.log`, absolute path via `GSD_RUN_LOG`) -- the run timeline. Every line: `<ISO8601-UTC> <TYPE> key=value ...`. Locked TYPE vocabulary: `RUN_START`, `HEALTH_PASS`, `HEALTH_FAIL`, `PHASE_START`, `PHASE_COMPLETE`, `PHASE_PARKED`, `PHASE_FAILURE`, `AUTH_FAILURE`, `PERMISSION_DENIAL`, `CONFLICT_ROUTED`, `CONFLICT_ROUTED_FAIL`, `MERGE_PARSE_FAIL`, `WORKTREE_FALLBACK`, `STUCK_FLAG`, `RUN_STOP`, `RUN_COMPLETE`. Typed tokens make the log grep-clean [LOCKED, Specifics]. Exact line format details are planner discretion within this vocabulary.
2. **`DECISIONS.jsonl`** -- per-decision spans (decision, evidence, confidence, escalated, phase) written by the escalation evaluator inside autonomous-loop (Phase 10/11 machinery, active because `GSD_RUN_ID` is set).
3. **`agent-trace.jsonl`** -- existing subagent telemetry hook covers spans below the autonomous-loop boundary (planner/executor spawns), unchanged.

Span hierarchy: run (`RUN_START`..`RUN_COMPLETE`) > phase (`PHASE_START`..`PHASE_{COMPLETE|PARKED|FAILURE}`) > decisions (ledger lines carrying `phase`) > subagent traces. `run snapshot` at every phase boundary adds the stuck-detection pulse.

### Boundary Logging

| Boundary | What gets logged | What state is tracked | Format |
|----------|------------------|------------------------|--------|
| overnight-runner -> autonomous-loop | `PHASE_START phase={N} worktree={branch}` ; skill args | `GSD_RUN_ID`, `GSD_RUN_LOG`, phase number, worktree branch | run.log typed line |
| autonomous-loop -> overnight-runner | `PHASE_COMPLETE|PHASE_PARKED|PHASE_FAILURE phase={N} reason=...` + outcome record | `phases[]` entry in RUN-META.json (status, merge_clean, timestamps); ledger hash via `run snapshot` (stuck detection) | run.log line + RUN-META.json + snapshot |
| overnight-runner -> MAILBOX.jsonl | `CONFLICT_ROUTED phase={N} q={q-NNN}` / `PERMISSION_DENIAL phase={N} tool={name}` | q-NNN id, conflict_files, run_id | run.log line + mailbox JSONL entry |
| worktree merge -> overnight-runner | raw `--raw` JSON echoed into the phase record; `MERGE_PARSE_FAIL` on parse failure | `clean`, `conflict_files[]`, fallback mode | JSON captured, decision logged as typed line |
| run artifacts -> inbox-reviewer | report renders counts (decisions, escalated, parked/answered, phases) + skipped-line count | none (read-only) | plain text to terminal |

### Failure Diagnosis

| Agent | Failure detection signal | Where to look | Common root causes |
|-------|--------------------------|---------------|--------------------|
| overnight-runner | `HEALTH_FAIL` / `AUTH_FAILURE` / `RUN_STOP reason=...` in run.log; run.log missing entirely | `cat .planning/run/{run-id}/run.log` first, then RUN-META.json `status` | ESC-03 gate not passed; auth expiry (W0-1 caveat); relative GSD_RUN_LOG (writes landed in a worktree); mailbox append failure |
| autonomous-loop | `PHASE_FAILURE`/`PHASE_PARKED` line; `STUCK_FLAG` (identical ledger hash across consecutive snapshots) | run.log for the phase span -> `gsd-tools ledger list --phase N` -> park snapshot -> agent-trace.jsonl for subagent spans | escalation park (by design, not a bug); permission auto-deny mid-phase; max-turns/context exhaustion; ambiguous outcome |
| inbox-reviewer | report counts disagree with raw files; `N unparseable entries skipped` > 0 | rerun `gsd-tools run report {run-id}`; diff against `wc -l` of DECISIONS.jsonl/MAILBOX.jsonl; inspect skipped lines | corrupt JSONL line (interrupted write >4096B -- should not happen, investigate); wrong run-id; report reading transcript-adjacent files it must not (regression) |

**Reproduction path for a failed run:** (1) `grep -E 'FAIL|STOP|STUCK|DENIAL' run.log` -- the typed vocabulary makes this exhaustive; (2) identify the phase span; (3) `gsd-tools ledger list` filtered to that phase for the decision trail; (4) `gsd-tools mailbox list` for parked context; (5) the worktree branch (if not merged) still holds the working state for replay. No transcript replay is ever required -- that is the RUN-04 invariant and the harness trust constraint ("auditable from the ledger alone").

### Rationale

The debugging story this design answers: an unattended multi-hour run fails at 3am and the human gets one morning hour. Past pain (Pitfall 1/2 in 13-RESEARCH.md) is precisely *silent* failure -- OAuth expiry leaving a hung run, `clean:false` swallowed by exit-0. Every such case now has a mandatory typed line, which is why the TYPE vocabulary is locked in this contract rather than left to the planner: the grep contract is the observability API. "Standard logging" was never on the table; the zero-dependency constraint was the forcing function to make the artifacts themselves trace-shaped (typed lines, JSONL, run-id partitioning) instead of bolting on a tracer.

## Reflection & Self-Correction

| Field | Value |
|-------|-------|
| What triggers reflection | Runner level: stuck detection -- identical ledger hash across consecutive `run snapshot` calls at phase boundaries (Phase 12 primitive; runner owns invoking it [LOCKED]). Phase level: escalation contract evaluation per decision (Phase 11, unchanged). |
| Metrics checked | Ledger hash delta between snapshots; escalation verdict per decision; `permission_denials[]` count in phase result |
| What happens on failure | Stuck flag -> `STUCK_FLAG` in run.log + RUN-META flag (visible in `ledger list`); the phase is treated as failed and skip-to-independent applies. Park verdict -> mailbox + park snapshot + halt (Phase 12). No retry-with-modified-prompt loops at the runner level. |
| Iteration limit | Each phase runs exactly once per run -- no retries. Skip-to-independent terminates when no phase remains whose `depends_on` chain is unblocked; then `RUN_STOP reason=no-independent-work`. Hard structural cap: the roadmap phase list is finite and never revisited within a run. |
| Tied to evaluation criteria | Test Contracts TC-2 (conflict routing), TC-4 (park bifurcation), TC-6 (stuck flag) below |

### Rationale

The runner is deliberately non-reflective: its failure mode is "wrong and obvious" (a phase failed, parked, or stalled), which needs guardrails and routing, not self-correction. Reflection-shaped judgment already exists at the right layer -- the escalation contract inside discuss-phase decides proceed/park per decision, and it was calibrated against a golden set (ESC-03) precisely so it can run unsupervised. Adding runner-level retry loops would undermine the audit posture (a retried phase produces two ledger trails for one outcome) and risk overnight token burn on a phase that will fail the same way twice -- the stuck detector exists because non-progress, not failure, is the expensive overnight pathology.

## Security & Permission Boundaries

| Agent | Allowed Tools | Denied Tools | Scope Constraints |
|-------|---------------|--------------|-------------------|
| overnight-runner | Bash (sandboxed), Read, Skill(gsd2:autonomous) | `--permission-mode bypassPermissions` / `--dangerously-skip-permissions` at any spawn [LOCKED, user override of research prescription]; direct writes to MAILBOX.jsonl/DECISIONS.jsonl (must go through gsd-tools); `git push`; crontab installation (documented only); editing settings.json | Writes confined to repo + `.planning/run/{run-id}/`; worktrees under the repo's worktree root; network only via pre-allowed domains |
| autonomous-loop | Existing workflow grants (Read, Write, Edit, Bash sandboxed, subagent spawns, WebFetch/WebSearch on pre-allowed domains) | Same denials as runner; plus: no merge execution (the runner owns `worktree merge`) | Per-phase worktree CWD; main-tree writes limited to `.planning/` via absolute `GSD_RUN_LOG` and gsd-tools |
| inbox-reviewer | Bash (gsd-tools mailbox/run subcommands), Read | Phase execution tools; resume/replay actions (Phase 15 scope) | Read run artifacts; write only mailbox answers via `gsd-tools mailbox answer` |

**Prompt injection defense approach:** sandboxed execution + worktree isolation + append-only ledgers, not input sanitization. The overnight workload reads repo content and web research results -- both injectable surfaces. Bounding the worst case: (1) sandboxed bash means an injected "delete X / exfiltrate Y" either fails in-sandbox or hits the regular permission flow, which in headless `-p` mode **auto-denies and continues** (probe-confirmed 2026-06-12: exit 0, model sees "the command was denied", structured `permission_denials[]` in result JSON) -- the denial is then routed to the mailbox, so an injection attempt becomes a *visible morning question*, not an action; (2) worktree isolation bounds file damage to one phase's branch, reviewable before merge; (3) append-only ledgers mean an injected agent cannot rewrite its own audit trail. Network egress is allow-listed: the runner's settings profile pre-allows `sandbox.network.allowedDomains` + `permissions.allow` rules for `WebFetch(domain:...)`/`WebSearch` [LOCKED] -- new domains auto-deny->mailbox rather than prompt-hang.

**Input validation strategy:** validated at the tool boundary, not the agent boundary -- gsd-tools CLIs are the chokepoints (ledger/mailbox schema validation at write time, run-context gate, q-NNN allocation). The runner validates the two things tools cannot: `GSD_RUN_LOG` absoluteness (health check) and worktree-merge JSON parseability (fail-safe to conflict). Rejected inputs are logged-and-routed (mailbox), never silently dropped.

**Credential surface:** no new credentials. No `ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN` mandate [LOCKED, user override -- their overnight sessions sustain auth; W0-1 expiry caveat preserved for the record]. The safety net is the startup health check (auth verification probe) + loud `AUTH_FAILURE` + hard stop. The runner never echoes env vars into run.log. Root check is omitted from v1 (only relevant under bypassPermissions, which v1 never uses); if the bypass posture is ever revisited, the root check returns with it.

### Rationale

Least privilege here is mostly inherited: the sandbox already constrains bash, gsd-tools already gates writes, worktrees already bound blast radius. The two denials this phase actively adds are the load-bearing ones: (1) **no bypassPermissions** -- the research recommended it, the user overrode it, and the override is sound for this threat model: the expected workload (research/plan/write) never needs sandbox escape, so every escape attempt is by definition anomalous and SHOULD surface as a morning question; (2) **no direct JSONL writes** -- the audit guarantee ("auditable from the ledger alone") only holds if every writer goes through the validating chokepoint. Worst-case injection outcome under this posture: a wasted phase and a weird mailbox entry. Worst case under bypassPermissions: arbitrary auto-approved writes at 3am. That asymmetry decides it.

## Error Handling & Failure Modes

| Failure Scenario | Affected Agent(s) | Detection Method | Recovery Strategy | Fallback Behavior |
|------------------|--------------------|------------------|-------------------|-------------------|
| Auth failure (token expiry, logged out) | overnight-runner, autonomous-loop | auth error string / `authentication_failed` / non-zero exit on the phase invocation; startup probe in health check | NONE by requirement -- `AUTH_FAILURE` + `RUN_STOP` logged, run stops (RUN-03: never silently retry) | Morning report shows the stop point; W0-5 says if this fires in practice, the auth prescription gets revisited |
| Merge conflict (`clean:false`, exit 0) | overnight-runner | parse `worktree merge --raw` JSON, check `clean` field -- exit code is insufficient by design | route structured entry to MAILBOX.jsonl via `gsd-tools mailbox append`; `CONFLICT_ROUTED` line; leave branch unmerged for morning review | skip-to-independent; if mailbox append fails: `CONFLICT_ROUTED_FAIL` line preserves evidence, phase marked failed |
| Merge JSON unparseable | overnight-runner | JSON.parse failure on `--raw` output | treat as conflict (fail-safe), `MERGE_PARSE_FAIL` line, route raw output to mailbox | same as conflict path |
| Worktree creation fails (sandbox) | overnight-runner | `{ok:false, fallback:"in-place"}` from `cmdWorktreeAdd` | run phase in-place, `WORKTREE_FALLBACK` warning line, record `worktree:"in-place"` | isolation lost for that phase -- acceptable, logged, visible in report |
| Permission auto-deny mid-phase | autonomous-loop | model-visible denial (in-session) + `permission_denials[]` in result JSON (runner backstop) | model writes mailbox entry; runner appends backstop entries for any denial lacking one; `PERMISSION_DENIAL` line | phase continues (probe-confirmed: `-p` mode continues on deny, exit 0); need surfaces as morning question |
| Park-and-ask verdict | autonomous-loop | `PHASE PARKED` sentinel + mailbox pending entry + park snapshot (Phase 12 machinery) | `PHASE_PARKED` line, outcome record `parked`, skip to next independent phase | when nothing independent remains: `RUN_STOP reason=no-independent-work` |
| Stuck phase (no progress) | autonomous-loop, detected by overnight-runner | identical ledger hash across consecutive `run snapshot` calls at phase boundaries | `STUCK_FLAG` line + RUN-META flag; phase treated as failed; skip-to-independent | flag visible in `ledger list` and morning report |
| Ambiguous phase outcome | overnight-runner | no sentinel, no clean completion signal after Skill return | record `failed` with `reason=ambiguous-outcome` -- never assume success | skip-to-independent |
| run.log written to wrong tree | overnight-runner (worktree CWD trap) | health check validates `GSD_RUN_LOG` is absolute before any phase starts | prevented structurally: path computed at run init, pre-worktree, exported absolute | health check failure if misconfigured -- run never starts |
| Morning report on corrupt JSONL | inbox-reviewer | JSON.parse failure per line | skip line, count, print `N unparseable entries skipped` | report always renders; skipped count > 0 is itself a diagnostic signal |

### Rationale

The rows were derived by walking each boundary in Communication Contracts and asking "what is the worst silent outcome here" -- and every recovery resolves the same way: convert the failure into a typed run.log line plus (where a human decision is needed) a mailbox entry, then keep doing independent work. Two failures intentionally have NO recovery: auth (requirement-mandated hard stop -- retrying produces a night of nothing while appearing alive) and stuck phases (retry would re-burn the same tokens). Not modeled: LLM rate limiting (the CLI's own retry machinery handles transient 429s; only terminal failure reaches the runner, where it lands in the `PHASE_FAILURE` path) and concurrent-run collision (v1 is one sequential run; nothing prevents two manual launches, but separate run-ids keep artifacts partitioned -- documented hazard, not a guarded one).

## Reasoning & Planning Approach

- **Sequencing is hardcoded, not decided:** roadmap order with a precomputed `depends_on` graph (parsed from ROADMAP.md -- mechanism is Claude's discretion [LOCKED]); skip-to-independent is a graph walk, not an LLM judgment.
- **Decomposition is inherited:** each phase runs the existing discuss→plan→execute chain via `Skill(skill="gsd2:autonomous", ...)`; overnight.md does NOT rewrite the loop inline [LOCKED]. While in autonomous.md, align lines :255 ("3-4 grey areas with ~4 questions each") and :276 (4-question cadence) with the adaptive triage-first depth style [LOCKED, Phase 10 carry-over].
- **Intermediate state is fully inspectable:** RUN-META.json `phases[]`, the ledger, and run.log expose the run's plan-in-progress at any moment; `tail -f run.log` is the live view. No HITL override mid-run by design -- the override surface is the morning inbox.
- **Prompting reliance:** typed run.log vocabulary and the `PHASE PARKED` sentinel are the two string contracts the workflow prompt must emit exactly; everything else flows through gsd-tools CLIs with schema validation.
- **Planner flexibility:** overnight.md internal step structure, health-check ordering (anchors: ESC-03 gate, auth verification, git tree state, GSD_RUN_LOG absoluteness), report layout, `--run-id`/`--from` flag handling, and the crontab documentation block are all discretionary within this contract.
